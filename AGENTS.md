## Guidelines

- See [Development](README.md#development) for how to run and test.
- **The default is no comment.** Write one only where the code is tricky and the reason is not obvious from reading it: a gotcha, a workaround, a magic value an API insists on, an ordering that matters. Not a restatement of the line below it, not design rationale, not a heading over a block, not a summary of what a function does. If the comment could be deleted without a reader losing anything, it should be.
- If an API is called "getConfiguration", use "configuration" not "config" in code.
- **A folder is what a person sees; a dir is what the code holds.** Every label, caption, menu item and message says **folder**; every configuration key, proto field, path variable and function naming a path says **dir**. The boundary is where a path stops being a place somebody picked and becomes a string something resolves, so `chooseScriptsFolder` writing `SetScriptsDir` is not a disagreement.
- Don't run `go build` directly; use `scripts/server`, `scripts/desktop`, `scripts/desktop-build`, or `scripts/docker`. Kill `scripts/server` when done, and check the port is free first.
- Don't run `scripts/build-ui` separately — a `-tags development` server rebuilds the UI on page load. Testing the server packages needs the same tag, or they embed a production bundle nothing has written.
- The build scripts are idempotent: they install tools at the version the relevant `go.mod` names and re-run protoc/bindings only when the inputs moved. The server's stamps are in `server/build`, the desktop's are Task's own in `desktop/.task`, and deleting either is always a way back.
- Don't update generated files directly (`ui/src/server/` from protoc-gen-kaja, `ui/src/bindings/` from `wails3 generate bindings`); they will be overwritten, and formatting one makes the next generator run a diff.
- Don't commit changes to `kaja.json`.
- Use past tense in pull request titles and commit messages ("Fix bug" → "Fixed bug").
- **A pull request description is one paragraph, one or two sentences**, saying what changed and why. Nothing else goes in it: no heading, no bullet list, no test plan, no account of what was verified, and no second paragraph. The reasoning belongs in the commit message, which is the long-form one — a description that summarises it is the same text twice.
- Use capitalized "Kaja" for user-facing labels; lowercase "kaja" for code, commands and paths.
- Don't reference specific example services (names of APIs used to reproduce a bug) in code, comments, or tests — they are just random examples.

### What belongs in this file

**This file is for what the code cannot tell you.** A sentence earns its place only if it is one of four things: an **invariant** that spans files and would be broken by a change that looks local; a **boundary** something must not cross; a **decision** whose reason is invisible where it was made, including one that was considered and rejected; or a **gotcha** a platform, a library or a wire format insists on. Everything else is read off the code.

**So don't write down** pixel sizes, class names, label text, key bindings, listings of files, symbols or menu items, what a function does, how a screen is laid out, or an account of what a change replaced. Each of those is a second copy of something the code already says, and the copy is what goes stale. Naming a file is for pointing at where a rule lives, not for describing it.

**Prefer editing to appending.** A change that contradicts a sentence rewrites that sentence rather than adding a second one beside it. Most changes belong nowhere here at all: if a section is gaining a paragraph per pull request it has become a changelog, and this file is what is true now.

### UI conventions

- shadcn/ui-style primitives over Base UI (`@base-ui-components/react`) + Tailwind, stock neutral theme. Reusable primitives live in `ui/src/components/`; compose them with Tailwind utilities. Reach for a raw HTML element + Tailwind before adding a primitive, and **ask before adding a new shared primitive** — one-off compositions are fine.
- Icons come straight from `lucide-react` under their real names. Compose class names with `cn()` from `ui/src/cn.ts`.
- **The four protocol marks are the one exception** (`ui/src/protocolMarks.ts`): lucide has nothing that tells four protocols apart when they are all servers reached over the wire. They are built with lucide's own `createLucideIcon`, so they type as a `LucideIcon` everything taking an app's icon accepts, and the test each has to pass is 13px in muted grey. Adding a fifth is not how an app type gets an icon: reach for lucide first.
- **A bundled server's brand mark is the other exception** (`ui/src/brandMarks.tsx`): the point of a known-server row is that it is recognised before it is read, and nothing on lucide's grid can be drawn into GitHub. So a mark is the company's own artwork under a license that allows it, at 16px in `currentColor` so it sits at the weight of the lucide icons beside it. It is not a `LucideIcon` and takes no place one does — a `BrandMark` is only ever drawn on the rows and the chip that name that server.
- **No em dash in a label.** Prose in the codebase uses them freely, but a string the product shows breaks at a full stop, a colon or a comma instead. An em dash in a 12px caption reads as generated copy, and the sentence it joins is usually two sentences. A `—` standing alone as an empty cell is a glyph, not a label, and stays.
- **A button carries one tooltip, never two.** `IconButton`'s `tooltip` says which, because a framework tooltip and a Base UI trigger would otherwise both claim the `render` slot.
- Base UI: interactive parts take a `render` prop (not `asChild`); the trigger wrappers here re-expose `asChild`. Overlays are `Popup` + `Positioner` + `Backdrop`; cursor-anchored menus take an `anchor`. Enter/exit is CSS keyed off `data-starting-style` / `data-ending-style`.
- **Three surfaces.** Content (every view body) is `bg-background`; chrome (sidebar, command row, status bar) is `bg-chrome`; floating (dialogs, popovers, menus, Monaco widgets) is `bg-card`/`bg-popover`. `bg-muted` is a highlight for chips and pills, never a pane. Status is amber for warning, emerald for success, `destructive` for error, each over a `/10` tint of itself.
- Theme tokens live in `ui/src/tailwind.css`. Day/night is a `dark` class on `<html>`. Monaco can't read CSS variables, so `ui/src/monacoTheme.ts` repeats the surfaces as hex — keep them in step.
- Tailwind is compiled by the Tailwind CLI (via `bun`) in an esbuild `OnStart` plugin in `server/internal/ui/builder.go`; the generated `server/build/tailwind.css` is imported by `main.tsx`.

### Configuration

- The server serves its workspace **read-only**; `scripts/server --editable` lets the UI write it. The desktop always owns its workspace. Decided at startup — the file never says whether it may be edited. It is **one** answer, `Runtime.can_update_configuration`, and it covers everything in the workspace: kaja.json and the scripts folder are written by the same process or by neither, wherever the folder is.
- **The scripts folder is the one thing whose place is the person's to choose** (`desktop/scripts_folder.go`). Scripts are ordinary files, so pointing kaja at a folder the machine already syncs is the whole of how two installations come to be looking at the same ones, with no server of kaja's and no account of its own. **kaja.json does not move with them**: it holds the apps a script imports, so leaving it in the container is what keeps a second installation from opening on an empty Kaja. The price is that the apps a shared script imports are each machine's to configure.
- Choosing it **rides a Wails event** rather than a bound method, the way a `kaja://` link and the zoom do, which is what keeps the native picker out of the generated bindings; the web passes no handler, so the control is absent where there is no picker. It reloads the window, because every script view, console and stored run names its file by an absolute path and the page reads the folder that is now open as it starts. The apps are untouched, so nothing recompiles.
- **The folder is named in kaja.json** (`Configuration.scripts_dir`), because where a workspace keeps its scripts is a fact about that workspace. Empty is the folder beside the file; a **relative** path is resolved against kaja.json's own folder, so a checkout can carry one; an **absolute** path names a folder elsewhere on this machine. It is read per call rather than held, so an edit to the file takes effect on the next listing. What stays in the container is the sandbox **bookmark**, because a path is a string and access is not: the picker is what grants a sandboxed kaja a folder outside its container, which is why bookmarks are restored before the folder is first resolved.
- **A named folder that isn't there falls back to the default and says so**, rather than being created: an unplugged disk's mount point is a path that looks writable, and scripts written there are ones the disk coming back would hide. The name is left in the file and the fallback is per call, so the folder is used again as soon as the disk or the sync comes back.
- **A read-only configuration omits the verbs that write it rather than disabling them.** The exceptions are the ones where the control is the clearest statement of a settled fact — the app form's disabled fields, because reading an app's configuration is still worth doing, and the MCP page's disabled switch, which omitted would read as a page that is broken. Every screen that drops its verbs says so in one full-bleed banner (`ReadOnlyBanner.tsx`) naming the one thing that is its own, rather than in a hint beside each missing control: the answer is about the workspace rather than about the screen.
- `Configuration` is the file and nothing else. `Runtime` is the running kaja — settled at process start, never read from or written to `kaja.json`, never accepted as input. It rides alongside the configuration on `GetConfigurationResponse` so saving can't round-trip it. `variable_status` is a third thing: the result of resolving one against the other.
- **A configuration change is a stream on the Api service, not a transport of its own.** `WatchConfiguration` sends the whole of what `GetConfiguration` answers with each time the file changes, so nothing is fetched after being told and there is no branch on which build is running — the desktop's webview reaches the same door a browser does. It says nothing when it opens, because whoever opened it has just read the file; a stream that ends is opened again, which is all a client has to do about a process that went away.
- **`mcp.enabled` is on `Configuration` deliberately, and it reads at first like `Runtime`** — whether this kaja opened a listener. It lives in the file because that is what makes it survive a restart, what lets a deployed workspace ship an agent session already on, and what makes it **one answer for the workspace rather than one per browser**. It is written by an RPC of its own rather than by `UpdateConfiguration`, because the file is read again where it is written, so flipping the switch never resends the apps and variables beside it.
- Retired fields are reserved on `Configuration` **and** stripped in `migrateConfiguration` — reserving only stops the schema reusing them, while protojson still fails the whole file on the unknown key.
- **protojson writes kaja.json and `encoding/json` lays it out again** (`SaveConfiguration`). protojson varies its own whitespace on purpose, settled per binary, so the same configuration written by two builds is two files and adding one variable was a diff touching every line of a file people keep in a repository. `json.Indent` over a compact encoding writes its own separators, so what lands on disk depends on the content and nothing else.

## Directory structure

```
desktop/          Desktop app (Wails)
protoc-gen-kaja/  Protoc plugin for TypeScript codegen (Go, own go.mod)
server/           Backend (Go) — serves both web and desktop
ui/               Frontend (React/TypeScript)
workspace/        Demo workspace, also what both public deployments serve
scripts/          Build and development scripts
docs/
```

Build output is gitignored and disposable: `server/build/` (protoc plugins, bundled UI assets), `desktop/.task/` and `desktop/build/bin/`, `desktop/frontend/dist/` (copied from `server/build`), and `$TMPDIR/kaja/` for compilation temp folders. `desktop/build/` itself is committed — it holds `config.yml`, the icon source and the plist templates.

**Development vs production** is a Go build tag. `-tags development` uses `server/assets_development.go`, which reads UI files from disk and calls `ui.BuildForDevelopment()`. The default embeds everything via `//go:embed`. `BuildForDevelopment` rebuilds when the **digest** of `ui/src` moves — content, not mtimes, because a checkout or `cp -p` restores old mtimes and an edit that isn't seen is served stale. A failed build leaves the last good bundle in place, so the next request retries.

**Server (web)** is one Go binary with the UI embedded, on port 41520. **Desktop** is Wails v3, embedding `frontend/dist` copied from the server build.

### The desktop, and what v3 moved

`wails.Run(&options.App{…})` is three steps now: `application.New` takes the services and the assets, `app.Window.NewWithOptions` opens the window, `app.Run()` blocks. What a v2 `runtime.*` call took a context for is a method on the application or on the window, so `App` holds both instead of a `ctx` and the startup and shutdown hooks are `ServiceStartup`/`ServiceShutdown` on the service itself.

- **The desktop build is `desktop/Taskfile.yml`, and `wails3` is what runs it.** Task ships inside the `wails3` binary, so the version `desktop/go.mod` pins is the runner too. `scripts/desktop-build` is the bootstrap in front of it and `scripts/desktop` is the same bootstrap in front of `wails3 dev`. A task states its `sources` and Task skips it while their checksums hold — content rather than mtimes, for the reason `BuildForDevelopment` reads a digest; `generate:bindings` also lists what it `generates`, because the bindings are committed and a stamp can only say what was last written, not that it is still there.
- **`desktop/build/config.yml` is the project's configuration and the product's identity.** `wails3 dev` reads `dev_mode` from it, `main.go` embeds it for the name, version and copyright, and the plists are rendered from it by `scripts/common` — a shell function rather than a task, because `{{ProductName}}` in the templates is what Task's own templating would try to resolve. There is no `wails.json` in v3.
- **A call is not a binding.** `webviewHandler` (`desktop/main.go`) mounts the lanes `router.Mount` registers beside the UI's asset handler and hands the mux to Wails, so the webview fetches `/Api/…` and `/app/…` on `wails://localhost` exactly as a browser fetches them on `:41520` — one client, one framing, one out-of-band channel, and no transport of the desktop's own to keep in step. A binding is for what only the desktop can do at all: the native dialogs, revealing a file in Finder, `kaja://` links, the resolved variables. **The scripts folder is not one of them** — it is the Api service's, so whether a write is refused is a question about the process rather than about the platform the UI is on. The agent switchboard is mounted there too: a binding is not what a stream is carried on.
- **`navigator.clipboard` cannot be assumed** — it exists only in secure contexts, which the desktop webview's page is not (nor is a kaja served over plain http). Every copy goes through `copyText` (`ui/src/clipboard.ts`), which uses the runtime's `Clipboard` under Wails and reports whether the text landed, so a copied checkmark is never shown for a copy that didn't happen. **Monaco's clipboard is that one too** (`monacoClipboard.ts`): its own service opens a `clipboard.write` on every click and keydown to hold a gesture, each refused and logged in the desktop webview. Monaco takes an embedder's service only before it instantiates its first one — `monaco.editor.defineTheme` is enough to do that — so the override runs at that module's own load and the module is main.tsx's first import.
- **Nor is any other secure-context API, `crypto.randomUUID` above all.** Every id comes from `uuidV4()` (`ui/src/uuid.ts`), which falls back to `crypto.getRandomValues`; `kaja.uuidV4` is that same function handed to scripts.
- **`$HOME` is not the person's home, and a path of theirs is reached through Finder rather than opened.** The sandbox points `$HOME` at kaja's own container, so `os.UserHomeDir` answers with that — which is what `appSupportDir` wants and what every path belonging to somebody else does not. `os/user` reads `pw_dir` through the directory service, which the sandbox leaves alone, so that is what a path outside the workspace is built from (`homeDir` in `mcp_bridge.go`). Getting *to* one is the other half: `NSWorkspace openURL:` fails silently on a folder kaja has no access to, while `activateFileViewerSelectingURLs:` is performed by Finder on kaja's behalf and needs no access at all. So `selectInFinder` is what everything outside the workspace goes through, `openFolderInFinder` is for the workspace's own folders, and a `stat` that is *refused* rather than absent is read as "can't tell" and the path handed over anyway.
- **The runtime is an npm package with side effects** — it takes over the context menu, watches for drag regions, and warns to the console when it finds no host. The web serves the same bundle, so `ui/src/wails.ts` reaches both it and the generated bindings through `import()`: esbuild keeps them in the bundle and evaluates them only when something asks, which on the web is never. `isWailsEnvironment()` asks the host for its message channel rather than for `window.go`, which v3 does not define.
- **The native menu carries what makes something, and nothing about what is on screen.** A menu item is enabled wherever the window is, so anything conditional on what is open belongs on the command row or a row's own menu, where its absence is the answer. Every shortcut a window states is the window's own keydown, so it works in a browser too; the menu's accelerator would be macOS taking the same key first, which is why the menu states none.
- **Zoom is the webview's own page zoom, and the desktop is the only build that has to state it**, a browser having an address bar that holds that control. Page zoom is the one that **reflows**: the layout is measured in the same CSS pixels and simply gets fewer of them, so every rect, media query and popover anchor go on agreeing with each other. CSS `zoom` scales what is drawn without moving what a popover is anchored to, and Wails' own `SetZoom` is `magnification`, the pinch zoom, which neither reflows nor goes below 1 — so it asks the process behind the webview for `WKWebView.pageZoom` over an event (`page_zoom_darwin.m`). **The window buttons are what the zoom does not scale**, being the system's own, so the band they are centred on is a different number of points at every zoom and `alignTrafficLights` is called again with it; the layout's own half of that is `--zoom`.
- **A development desktop build serves `frontend/dist` off disk** (`assets_development.go`, `KAJA_FRONTEND_DIR`), so a UI change is `⌘R` rather than a rebuild of the binary it would otherwise be embedded in. The Wails watcher restarts the app on Go changes alone.
- **`scripts/demo` photographs the shipped app for the App Store**, driving `/Applications/Kaja.app` against a staged workspace. It navigates by `⌘P` alone — the window is a webview, so there is no control to address by name and a coordinate rots with the next layout change — which means **every query has to match exactly one destination**. Every shot is made opaque by a Swift helper the script compiles, because App Store Connect refuses an alpha channel and `screencapture` writes one into every PNG, which neither it nor `sips` can drop. The README's screenshot and the website's poster crops come out of that set, so both are refreshed by running it rather than photographed by hand.

### Code generation

```
server/proto/api.proto
  ├─ protoc-go + protoc-gen-go/go-grpc → server/pkg/api/*.go
  └─ protoc-go + protoc-gen-kaja      → ui/src/server/*.ts
                                          └─ esbuild (cmd/build-ui) → server/build/
                                               → embedded in server / copied to desktop / embedded in docker
```

`protoc-gen-kaja` generates TypeScript, currently a drop-in replacement for `@protobuf-ts/plugin` producing identical output (it will diverge). At runtime both protoc-go and protoc-gen-kaja are **embedded as Go libraries** — no subprocesses; the binaries are only used by development scripts.

**The internal `Api` service is spoken as gRPC**, like everything else kaja calls. `protoc-gen-go-grpc` is generated for one thing — `Api_ServiceDesc`, the dispatch table `ApiService.Invoke` looks a method up in — and no `grpc.Server` runs: both builds answer `POST /Api/<Method>` with `internal/grpc.Serve`, which is the app lane. It is generated with `require_unimplemented_servers=false`, so a method missing from `ApiService` fails the `var _ ApiServer` assertion rather than compiling.

- **`Invoke` hands back an `apps.Stream` rather than a message, so a server-streaming method needs no door of its own.** Whether a call answers with one message or many is the service's to say. A generated streaming handler *writes* where an `apps.Stream` is *read*, so `serverStream` is both halves at once and the handler runs on its own goroutine for as long as the call does; a send gives up on the request's context, so a browser that went away leaves nothing parked.
- **Two methods stream.** `Compile` carries the compilation's log as it is written, then a last message carrying the verdict and the generated sources — the log *is* the stream, so no compiler outlives the call that made it. `WatchConfiguration` stays open for the life of the window.

**Everything is generated with `force_optimize_code_size`** — a message type is then its field descriptors and nothing else, and the runtime drives `create`, `internalBinaryRead` and `internalBinaryWrite` off them, producing the same bytes and the same defaults. That is over half of what a message would otherwise generate, and an app is compiled and bundled in the browser reading it, so the specialized codec is paid for by the person waiting for the app to open against calls a person makes one at a time.

- Tests in `protoc-gen-kaja/tests/` compare output against `protoc-gen-ts`; run with `protoc-gen-kaja/scripts/test`. **Every test runs twice**, once in each optimize mode, since both are output this plugin produces. `tests/000_big` is the multi-file integration test covering the whole surface — scalars, WKTs, every streaming kind, custom options, `import public`, keyword field names, name collisions and the comment edge cases. **Extend it when adding codegen features.**
- `protoc-gen-kaja/scripts/loop` alternates two agents: RALPH (fixer, reads `RALPH.md`) and NELSON (adversarial tester, reads `NELSON.md`).

### The demo workspace

`workspace/` holds the demo apps and scripts, and both public deployments serve it out of the Dockerfile's `demo` stage. **A demo script carries no comments**: it is the picture of what a script looks like, and a paragraph over the code was the first thing the pane showed of a script the window had to scroll. The deployments are `demo.kaja.tools` and a per-PR app, and they differ in one thing: a preview is served `--editable` and the demo is not, a preview being a scratch copy that is rebuilt on every push and destroyed with the pull request. The **main** workflow drops two apps with `jq` before deploy so the public demo shows fewer, and fails on a name no app has. Nothing in kaja knows a deployment can hide an app, and it must not grow such a setting. The demo services themselves live in kaja-tools/website.

## Drafts, files and the sidebar

**Everything you run is a script; the only axis is whether it has a name.** A method in the sidebar is a template — clicking it fills a **draft**. The Scripts region is two groups, Drafts and Files.

1. **A draft has no name and no place; a file has both.** Not "temporary vs. permanent" — a draft survives quit and reopen exactly as a file does, so nothing about one is styled as a warning.
2. **Files never become drafts on their own.** Editing a saved file leaves it a file, auto-saving in place. The only ways into Drafts are running something with no file yet and a blank script; a variant of a file is a copy of the file.
3. **Saving a draft as a file moves it into Files.** The sheet asks for a name and a folder, nothing else.
4. **Discarding is safe.** Drafts are discarded without asking, edited ones included.

One word throughout — a **draft** (`drafts.ts`, IndexedDB, unlimited, web and desktop alike). **Four verbs, one object each**: you **save** a draft as a file, **discard** a draft, **delete** a file, **revert** a file to saved. Nothing says "unsaved", because nothing is at risk.

- **Clicking a method never asks what to do with it** (`onMethodSelect`). An **untouched** draft holding exactly this call is **reopened**; otherwise an untouched draft — byte-identical to its generated code and never run — is **taken over**, and a worked-in one is left alone while the call starts a new draft. The agent's draft is never taken over. Appending is deliberate (⌥click or the row's `+`) and `appendCall` merges import lines and edits the text rather than reprinting it, so the author's formatting survives.
- **Generated code is run through prettier before it reaches the model, and that is the only place a script's text is formatted**: the editor draws what it is handed. It formatted every buffer it opened once, and a file auto-saves, so opening one to read it rewrote it on disk. The exception is a generated module, which is printed by the TypeScript printer, lives in memory, and is nobody's file.
- **A draft names itself from its own code** (`draftTitle.ts`), re-derived on a run and on an append, never while typing. **There is no rename of a draft**: saving one as a file is what gives it a name. A draft that is still untouched is **dimmed** wherever it is named, and resolves to full weight when edited or run.
- **A draft is not bound to an app.** Deleting an app leaves drafts alone; they just stop compiling. Only a *rename* is followed, so imports keep resolving.
- **A rename is followed into every script, not only the open ones** (`followAppRenames`). An app is addressed by its name, so a rename is the one edit that leaves every import of it naming nothing — so each draft's code, each open buffer and each **file on disk** is rewritten, and a read-only workspace's files are left red and correctable. A rewrite touches the module specifier and nothing else, read off the AST, so the app's name in a string, a comment or a method call is left where it is; the text is spliced rather than reprinted.
- **What a rename is, is one rule asked twice** (`detectAppRenames`): a name that left the file and a name that arrived describing the same server. It is asked of the configuration to follow the scripts, and of what is compiled to remap the app rather than recompile it. An app whose parameters moved with its name is **not** a rename — it has to be reopened.
- **A remapped surface has to be followed by the app it is invoked on** (`Manager.Rename`). Not recompiling is the point of the remap, and `OpenApp` is the only thing that registers an app under a name, so a rename nothing tells the server about leaves every call refused with `is not open`. What the call moves is the instance, never a reopen: the parameters did not change, so reopening would read the upstream again for a surface that has not changed. Renaming a name nothing is open under is not a failure, since two windows watching one file both follow the same rename.
- **Monaco will not notice on its own that a module moved** (`revalidateOpenEditors`). TypeScript resolves a script's imports once and revalidates only when that script's own text changes, so an app renamed, deleted or reopened under an open editor leaves a dangling import green and a newly resolvable one red. Every configuration write that moves what an import resolves against pokes every open editor with an identity edit. It rides an effect rather than the `setApps` updater, because the renamed app's own models are written by that updater and a buffer rewritten before it ran would name a module that does not exist yet.

### One section, two groups

- **A control's scope decides where it lives.** **+** is local, so Scripts and Apps each have one; Variables and the MCP server are about the window, so they sit in the sidebar's own global band and are the only things there. Both open a view rather than a menu, which is the other half of why they are peers. On macOS the band takes the traffic lights' inset and stays draggable except where a control is; everywhere else the Kaja mark takes that corner, so desktop and browser differ by exactly one element.
- **Every control in the panel stands in one column at the right edge** — a group's verb, a row's hover actions, the run indicators — so a run starting under the cursor never moves the label. There is no leading slot and no dot of any kind, and **no counts**: a number over a list you can see is not something you can act on.
- **Delete and discard are different words.** Deleting a file is the only destructive-styled action in the sidebar; discarding a draft is neutral, has no dialog, and there is no route from a file into Drafts.
- **The pile is capped, not scrolled.** Drafts draws a fixed number of rows, edited ones pinned above browsing buffers, and the rest are `n more…`. **Nothing is removed on a timer.** A weekly sweep of the browsing buffers was tried and cut: a pile that empties itself is one you cannot leave something in, and the row it took was a setting about housekeeping in a menu of verbs. So the Drafts header's trash is the one verb, discarding all of yours on the click.
- **Empty states, on one rule: where there is an action, show the action; where there isn't, state the rule.** Zero drafts hides the group entirely; zero files states how a file comes to exist, since there is nothing to offer; zero apps is a real row, since that list *can* be filled from here. Nothing there is a full sentence with a full stop, and none of it says "configured", which is kaja.json's word rather than the window's.
- **Tabs were considered and cut.** The core loop is clicking a method in Apps and landing in a draft under Scripts; one region at a time hides half of it.

### There is one search, and it is the finder

`⌘P` is the whole answer. The sidebar had a filter of its own and it is gone: two magnifying glasses in one window is a question the reader has to answer first, and the finder strictly dominates — it matches every method by name, service and app, every file by name and folder, every draft by title, plus Variables and the compile log. What went with it is browsing a filtered catalog in place with the row verbs still attached; if that turns out to matter the fix is `⌥⏎` in the finder, not a second field in the panel.

### Folders

- **A folder in Files is a real directory** under the workspace's scripts root. Creating, renaming and moving hit disk immediately, and an **empty folder persists**.
- **A name is resolved inside the folder, never followed out of it.** Everything crossing into `server/pkg/api/scripts.go` — UI, agent, browser, on either build — is reduced to a relative path (`filepath.IsLocal`, no dot segments) and opened through an `os.Root`. An absolute path is the same name said in full, so a listing's own `path` can be handed straight back. **That is the whole access boundary**, and it is why the MCP bridge guards no paths of its own.
- **A file's path is its name**, so renaming and moving are one write and the rename field holds the whole filename. A `/` in what is typed files the file deeper and `../` walks it back out, resolved against the folder it is in and never followed out of the scripts root (`resolveScriptRename`, unit-tested).
- **Naming anything in Files is inline, never a dialog** (`NameField`): the row is real from the first keystroke, and making a file, making a folder and renaming either are all that one row, so the interaction is learned once. The sheet is only for saving a draft as a file — a file has a name and a place already. A rename starts from clicking the name of a row that already has the focus, which is why it carries no ellipsis; the gesture is on the **name**, not the row, so a folder's chevron goes on folding it. There is no `F2`: a key nothing on screen mentions is not the way a rename is found.
- **Moving a file is dragging its row, not a menu item.** The tree already draws every place a file can go. Every row names the folder a drop on it lands in — a folder row its own path, a file row the one holding it, the Files header the top level — so the answer never changes in a gap between rows. The transfer carries a **type of kaja's own**, which is what keeps a row let go over the editor from being pasted into it as text. Drafts have no place, so they neither drag nor take a drop, and the typed path is the keyboard's way to the same write.
- **Deleting a folder deletes what is filed there.** A folder is a place, not a container of its own, so the write is a `RemoveAll` rather than a refusal to delete a folder holding files; one that is already gone is not a failure. The UI prunes its rows only **after** the disk says yes.
- **Copying is Copy on the row and Paste on the place**, in a clipboard of the region's own rather than the system's, because a row is not text. Paste lands where a drop would and is **absent** rather than disabled where there is nothing to paste. The disk does the copy and refuses a name that is taken; the name is settled first against what is already there (`copyName`, unit-tested), the way a desktop file list numbers a duplicate. There is no Cut: moving is the drag.
- **Drafts stay flat, permanently.** A place is half of what a file is.

### Saving, and what the web hasn't got

- **A file auto-saves; a draft has no save step.** An open file view writes shortly after you stop typing, and on quit, close and before a rename (`flushScriptWrite`). A draft is written straight through to its store. Neither has an unsaved state, which is why neither has a dot.
- **A deployed kaja is the same app minus the verbs that write a file.** Drafts are IndexedDB on both platforms, so lists, titles, discarding and history are identical; everything that writes the scripts folder is missing. It is the *workspace* that is read-only, not the browser: `scripts/server --editable` has all of them.
- **Both builds read and write the folder the same way** (`scriptFiles.ts`, `server/pkg/api/scripts.go`): every verb is a call on the Api service, the desktop's window making it over the mux its webview already speaks. `canWriteScripts(runtime)` is the one place that says the answer is the configuration's own, and it is what the rest of the UI asks rather than asking which platform it is on.
- **A file the server can't write is read-only, stated by refusing the edit** — the editor takes `readOnly` rather than accepting keystrokes nothing would keep. A blank script, and `Duplicate as draft`, are how you take a copy somewhere writable.

### The agent's draft

A snippet run over MCP is run in **one** draft per client, the same one every time that client runs, so its runs appear in the sidebar and the run history.

- **One row per agent, pinned above your own and wearing its name**, read from the MCP `clientInfo`. `agentName` on the `Draft` is the whole of it, the slot included: the agent's buffer is found by that name rather than by an id held beside the list, so nothing can drift from it. Agent drafts are excluded from the count and from the header's discard.
- **One endpoint serves every agent, so a run says who made it** (`identify`), three ways, newest first: the revision that dropped the handshake carries `clientInfo` on every request; an older one announces it at `initialize` and echoes a session id; a client doing neither is whoever handshook last. A name is pinned a session **once**, so the map is bounded by how many agents there are rather than by how often they connect.
- **It can be cleared like any draft, and that is the only verb the row has.** **There is no way to save one as a file**: it is the agent's workbench, so the sheet would be asking you to name what somebody else wrote. **The agent saving its own is a different act** — `create_script` consumes the buffer when what was saved is exactly what was last run, so the buffer becomes the file rather than lingering as a copy, and its console follows it to the path.

## Deeplinks

**`kaja://run/<script>?key=value` is a script's address outside Kaja** (`scriptLink.ts`). A URL is what every launcher already knows how to build — a Raycast quicklink, an Alfred workflow, a Shortcut, `open` from a shell — and Kaja integrates with none of them. **The word is deeplink** wherever the product says it; where the sentence is about the string itself it still says **URL**.

- **The verb is the host and the script is the path**, which leaves the whole query to the script: nothing in it is reserved, so a script may take a parameter called `script` or `run`.
- **A page can't register a scheme, so the web says the same thing after a `#`.** One grammar, one parser — `parseScriptLink` puts the scheme back on, and nothing downstream learns which door it came through. A **fragment** rather than a path because a fragment is never sent to a server: no route to add, no SPA fallback, and the relative `./main.js` the page already loads stays correct. `linkBase()` is the one function that asks what it is running in.
- **The address carries no extension; a filename always does.** A deeplink is meant to outlive a rename or a move, and `.ts` in a path reads as "fetch this file". The cost is that two scripts can't share a name across extensions. A link written *with* `.ts` is still read.
- **Every value is text, and `kaja.input` is a map of them**, empty on a script that has never been run with any — never `undefined`, so `kaja.input.url ?? await kaja.askStr(…)` is the shape to write.
- **The input belongs to the file's last run, and Run repeats it** (`runInput.ts`). Every door writes it, and Run reads it, so pressing Run after a deeplink landed runs the same thing again, which is the whole of the edit-and-rerun loop a deeplink lands you in. A key the script has stopped reading is dropped rather than repeated, and the values a run carried are stated **on the run**, because what the next press will send has to be readable before it is pressed.

### One parameter block, three doors

Every flow that needs values shows the same middle (`ParameterSheet.tsx`): a grid whose keys are read from the source and whose values are **always real text fields** — a field clips at its own edge, scrolls on focus and stays correctable up to the run, where a line of static text does none of the three. A field carries **no tooltip**, because a tooltip opens on focus as well as hover and the sheet focuses the first field.

- **`copy` — the deeplink being built.** The URL is the headline, shown whole with scheme and keys dimmed, which teaches the scheme and the query syntax at once. A blank value still ships its key, and that trailing `=` is where a launcher's own token goes. The clipboard is the only exit.
- **`arrived` — the deeplink that came in.** The script is opened *behind* the sheet and `⏎` runs it. There is **no "don't ask again"** — a remembered answer is a policy, and this is the one door where the thing on the other side may not be a person.
- **`run` — the Run button asking first**, which is what makes a script written for a deeplink runnable from the app. Fields open on **what the file last ran with**, because that is what a plain Run is already carrying: a blank field under a Run that sends a value is the one thing it may not say.
- **The parameters are read at the language level** (`scriptInputs.ts`). `readInputKeys` walks the AST, not the text, because `kaja` is an ordinary local binding and a key is written several ways a pattern would miss or invent. A computed key is left out rather than guessed at, and a `kaja.input.x` in a comment or string is not a parameter.

### The Run button, split

Plain Run keeps its place and pressing it never opens anything. A caret beside it opens the script's action menu: run gestures, then what the script is once the run is over.

- **The caret is on for every script and the menu is what varies.** Keying it to `kaja.input` made the pill two widths and left `Copy deeplink…` unreachable on a script with no parameters. Mid-run the button is Stop and the caret is gone.
- **The second group is never empty.** A file offers its deeplink and a reveal; a draft offers `Save as file…` and `Discard`, a draft having no deeplink *because* it has no name, so the item in that slot is the one that fixes it. An agent's draft offers `Discard` alone.
- **A read-only file's answer is `Duplicate as draft`** — the one place a file may become a draft, because on the web a draft is all "take a copy and change it" can mean. The copy is taken from the **buffer** and lands with an empty `generatedCode`, so it is work rather than a browsing buffer the next method click would take over.
- **Omit, don't disable**, and **prefill is not a menu item** — the sheet opens on the last run's values because Run is sending them, not as a gesture of its own.

### Where the rest of it lives

- **The desktop holds the link, because a deeplink often launches Kaja.** macOS delivers the URL long before there is a webview, so `openLink` buffers until the UI emits `link:ready` and then flushes. It rides a Wails event in each direction. Registering the scheme is a bundle's job, so `CFBundleURLTypes` in the plist templates is the one place it is declared.
- **The web needs no buffer, because the URL is one.** The link *is* the page load, or a `hashchange`; a fragment arriving before the script list is simply left where it is. It is cleared once handed over (`history.replaceState`, which fires no `hashchange`) — the URL is a door, not a location.

## A filename is one object

`FileName.tsx` over `scriptNameParts`: the name at full weight, the extension quiet behind it, in every place a file is named. It is **stated, not read off the dot** (`file` is a flag on `ViewIdentity` and on a finder `Destination`), because a draft's title is a call with no extension to find. It is a fragment rather than an element, so the caller owns truncation, font and weight.

## The tree is an index

The tree is a dense desktop index, not a web page: depth is a hairline rather than an icon column, packages and services carry no icon, and the **app keeps its** `AppTypeIcon`.

### What the tree opens with

Expansion is a record of where you have been (`treeExpansion.ts`). Three inputs, in order: calls you made, folds you made, and — only before either can say anything — how much of an app fits on screen.

- **The ledger is what you called, most recent first.** A `MethodUse` is app/package/service/method; the list is ordered, so there is no timestamp or count. It is written from the one door the tree and the finder share and from every call a script makes. On load the tree opens the path to the most recent calls that still resolve, budgeted across the whole tree.
- **A fold is a decision, an expansion is a suggestion.** A node is `open`, `shut`, or absent; nothing derived overwrites the first two. Opening a node by hand clears its own `shut`, so the mess is never bigger than the nodes you touched. There is no global reset to offer.
- **Size decides only on a cold start** (`autoOpenNodes`): an app opens as deep as it goes while staying under budget, **a level whole or not at all**. Once there is a history, silence about an app means shut.
- **An app is seeded once**, when it first has services, so the tree can never rearrange under the cursor. Apps compile at their own pace, so `seedFolds` seeds *some* apps against *all* of them.
- **Folds are pruned against what exists; the ledger is not.** An app still compiling has nothing to match against, so its subtree is spared rather than cleared and re-seeded. The ledger is capped instead, because a failing compile would erase the history that outlives it.
- **There are no fold-all/unfold-all buttons.** ⌥click a row takes its subtree instead.

## A run has three views

**A run is the unit** (`runs.ts`): one press of Run, one duration, one verdict, everything it produced under it.

**And there is more than one at a time**, because nothing stops there being — Run twice, a deeplink arriving mid-run, an agent calling `run_script`. So the run is **lexical, not ambient**: `beginRun` mints the run *and* the `Kaja` its script is handed, and every callback is a closure over it. There is no "current run" to read, so there is nothing to read wrongly. A client is shared by every run that imports it, so its methods are **bound per run** (`Client.methodsFor`, memoized in a `WeakMap`) — the single assignment this replaced made two scripts report calls into each other's console, and made one script's `kaja.approve` send another script's writes without asking.

- **What belongs to the app rather than a run lives on `KajaHost`**: the workspace's variables and `LiveTables`. A page fetched from a canvas belongs to the run that drew the table, so the host routes a block id to its owning `Kaja` and the call lands in that run's log however long ago it ended.
- **A run's context lives exactly as long as something can call into it.** `settleIfQuiet` asks every run in flight, and dropping the settled record releases that run's `Kaja`, approvals, sampled methods and bound clients. Only a live table the canvas can still page holds it past that, and that registry is bounded.
- **A call a budget is holding is work the run has and the log hasn't** (`RateLimiter.waiting`). `kaja.rateLimit` admits a call *before* its row is written, so a held call is out of the log and out of the percentiles — the settle check is the only thing that knows about it, and a run whose last call is held would otherwise settle out from under it. **And what the settle check knows, the run says**: the count is stated beside the clock, or the only honest reading left is that Kaja is stuck.
- **A run leaves the live list one way, and that way gives it its duration** (`endRuns`). Settling and dropping are one act: the list is where the settle check looks, so a record taken off it without a duration is a run nothing can settle — and a run without a duration is a *running* run to everything that reports one. A duration is written **once**, because a run ending on its own and something ending it both reach there.
- **Stop is about one run**: it aborts the runs of the file the button is on and cancels only the questions those runs are parked on. It **ends** the run rather than asking the script to end it — a run parked on a question that will never be asked again has nothing left to settle it.

The **log** is the flat audit log — one row per call, in wall order, always complete. The **canvas** is the rendered output, free to fold what is repetitive. The **stats** are what the calls add up to. A segmented control switches them and **everything else about the header stops moving**; that is what pays for the split. Request/Response/Headers are on the payload pane, so the pane never reflows as you step through the log.

### What a script printed

`console.log` and friends are the logging API. There is no `kaja.log` — the `kaja` object holds the verbs that are Kaja's own, and a second spelling for logging would add a decision without a capability.

- **The scope is what tells a script's lines from Kaja's own** (`scriptConsole.ts`). The script body is wrapped in a function taking `console` as a parameter, so inside it the name resolves to the run's console and everywhere else to the real one — no origin tagging, nothing to drift. **Kaja's own `console.log` never appears in a run**: what fires during one is transport tracing that duplicates the payload pane. When the system has something to say in a run it says it as a row, a status or a tail-bar statement.
- **The wrapper is built from the console, not declared as five methods** — the five-method stand-in made `console.table(rows)` throw inside an agent's snippet. Anything that isn't a level passes straight through to devtools.
- **A printed line is not a verdict** (`printed` on `ConsoleItem`): it never colours the run's dot and never counts as something drawn, so a script that prints `console.error` in a loop and finishes is not a failed run.
- **Off by default, and a floor rather than four checkboxes** (`LogFloor`). Off is bearable because the tail bar states what was printed and is the way to turn the floor on.
- **A line lands where it was printed and a call where it was issued** (`callRows`), so a line printed mid-call sits after that call's row rather than after its response. Both lists are ordered, so the mix is a merge.
- **kaja.log gets the lines with their origin attached.** The script's console forwards to `deviceConsole`, the console as it was before `installUiLog` patched it, so a script error isn't written twice.

### The payload pane

**A response is printed, not formatted** (`payloadText.ts`). The pane follows the selection, which follows a run as it happens, so prettier's parser download per payload buys nothing over `JSON.stringify`. Being synchronous is the other half: a slow payload can't land over a newer one. Prettier stays where it earns its keep — generated TypeScript and the JSON document in the app form. Past a size cap the pane draws the head and says how much it left.

**A string that is itself a JSON document is read on request** (`embeddedJson.ts`). An API with nowhere to put structure puts it in a string — an MCP tool that declares no output schema returns its result as the text of a content block, and a field called `payload` does the same thing — so the document is there, escaped, on one line, and reading it is what the pane was opened for. It is **shape-driven rather than marked**: a mark on MCP's own `Content.text` would be the honest version of the same guess and would leave the reading absent from the gRPC and REST apps that do this just as often. Nothing about the call changes, on `unwrapEnvelope`'s rule — the wire, the generated type and what a script gets back are all still the string, and only the pane draws otherwise, only while it is asked to. **The toggle is absent where nothing parsed**, so the button appearing is how you learn there is a document in there, and the size stays the wire's own in both readings: how big the answer was is a fact about the exchange. Only an object or an array counts, because `"123"` parses too and a number an API chose to send as a string is a string. **A document inside a document is not read** — one guess on another, where the first wrong one takes the rest with it.

### What the calls added up to

`runStats.ts` computes it, `statsChart.ts` is the arithmetic, `Stats.tsx` draws it. **Nothing on the page is specific to a perf test** — everything is derived from what a call already records, so a paging loop has latency, throughput and concurrency like anything else; they are just not *shaped*. The segment is always there: a tab that appeared once a run was big enough would be a control you have to notice to know exists.

- **Charts are plain SVG in the view and numbers in a module.** Every one is a linear scale into a fixed box, so there is no axis to negotiate and no library to take, and `currentColor` is what makes day and night free without a second hex table to keep in step. **The hard half is bucketing, not drawing** — which is the half no chart library does.
- **The metrics are a buffer, maintained as the run happens** (`RunGroup.metrics`), never re-derived per repaint; `RunMetrics.version` is what the view memoises against.
- **Percentiles are exact while the values are few and a log histogram once they are many.** A script making a dozen calls reads its own numbers back; a perf test gets bounded memory and a stated worst-case accuracy, and the histogram *is* the distribution chart.
- **Time buckets double rather than being sized in advance** — a run has no length while it is running. A bucket index is derived from a timestamp rather than remembered, so the pairwise collapse that halves every index leaves a call that settles afterwards landing where it belongs. **Concurrency rides on the same buckets as a delta** (+1 issued, −1 settled): summing two deltas is what makes them mergeable, and prefix-summing is the line. **A slice is never finer than the calls it holds.**
- **The percentiles are of the calls that succeeded outside the warm-up**, and the strip says what that left out. A failed call's latency is how long it took to be refused; a warm-up call measured a cold server. Both are counted in requests, throughput, concurrency and the error rate — the exclusion is from the latency alone, and it is stated rather than silently applied.
- **Failures say the same thing three times**: marks on the chart floor, a segment at the foot of the rps bar, a count in the method table. The segment has a floor, because one failure in three hundred calls rounds to nothing and still has to be visible.
- **A schedule is the only perf-test-specific ink on the page**, drawn as bands behind all three charts so they read as one ruler; the plateau gets no tint, the bands existing to show where the schedule was doing something other than holding still. A plain run has none and loses nothing else.
- **Two degenerate cases are stated rather than drawn.** One call collapses to its duration and its outcome; zero calls is one line of muted text, not an empty dashboard with six dashes in it.

### The run a script asks for

`kaja.perfTest(body, options)` runs a body over and over on a schedule (`perfTest.ts`). **The body is one iteration**: `concurrency` virtual users each run it in a loop, and every call inside it is sampled. It is what makes a run *shaped* for the Stats page — and the page is a view over any run, so the two halves stay independent.

- **The budget is `iterations` or `duration`, never both**, and `duration` is the whole test with its ramps inside it. `rampDown` needs `duration`: with iterations the test ends when the last one does, which is nothing to ramp down from.
- **A numeric `warmup` is iterations and a string is time** — the unit a warm-up is naturally said in depends on what is being primed. Either way it resolves to one boundary in time, which is the whole of what the stats are told. **A warm-up whose end is not known yet holds its samples**, because a sample counted under the wrong phase cannot be taken back out of a histogram; it runs at one virtual user, so no call issued after the boundary started before it.
- **A failed call fails the iteration, not the test.** It runs to the end and the failures are the data. A body that throws is counted the same way and reported as `failedIterations`, which is not the same number as a failed call.
- **The report is the same computation the page is** — `perfTest` feeds a `RunMetrics` from the same funnel every call already passes through, so a script's own assertion and the Stats page can never disagree.
- **Asks and approvals throw inside the body.** Ten virtual users parked on one question is a deadlock wearing a dialog, so the verb refuses and names where the value should have come from.
- **The plan is made once and never chases the run.** A schedule that adjusted to the observed rate would report the server's behaviour as if it were the test's.
- **The block is live, on its own beat**, redrawn from the metrics as they fill so a test that runs for a minute says so for a minute rather than spinning and landing on a total. The beat rides the supervisor's tick rather than a timer of its own, since reading the metrics is real work and the test is the thing being measured.
- **A perf run opens on its stats**, outranking the canvas it drew on: the block it leaves there is a headline and a way to the page, not a second copy of it. The script is held to the same rule in the declaration's JSDoc and in the agent guide — the report is handed back to be *judged*, and a script that redraws the percentiles as a table has retyped the page it is standing on.

### The console belongs to the file

`consoles.ts`. There is no shared console: a run lands in the console of the script it was pressed on, so switching files switches consoles and coming back finds the runs, selection, tab and view as they were left.

- **Keyed by file**, not held on the view — views are a small cache and would throw a console away on ordinary navigation. `Consoles` maps a `fileId` (draft id or script path) to a `FileConsole`. ("Source" is taken: it means an app's generated proto TypeScript.)
- **A run is a buffer, not React state, and nothing above the console subscribes to it.** A call reaches the console two or three times, and when each was a `setHistory` at the root, a thousand-call run rendered the whole window a few thousand times over. The store is mutable and external; `Console` is the one component that subscribes. React holds only which file is on screen.
  - **Notification is coalesced to the frame**, so many calls between two paints are one repaint. A **gesture** — a click, a run starting or ending, a question drawn or answered — notifies at once.
  - **What a run says about itself is counted, not derived** (`ItemStats`). `add` is idempotent so a settling call is an update rather than a recount. The pure functions this replaced are kept as the definition it is tested against.
  - **The sidebar's three sets are three booleans per file** (running, agent-run, waiting), published on their own subscription so a flip is rare and a call never touches them. **Settling hangs off the store, not off a render** (`subscribeQuiet`).
- **An item is anything that happened in a run** — a call, a block the script drew, or a printed line. Blocks are items rather than a parallel world, so they inherit grouping, ordering, the per-file console and the store.
- **Both caps have to let go of what they drop.** A file keeps a bounded number of runs and a bounded number of consoles, letting go of the least recently touched — never one whose run is still going. A run trimmed off the list while the by-item and by-call indexes still pointed at its items was a file that grew with every run it had ever held.
- **The row and the payload leave the heap separately**, because only one costs anything: a run keeps every row up to a large cap (past that it says how many it stopped keeping), while a file keeps the payloads of a much smaller number of recent calls in memory. Retention is by count rather than bytes, because measuring bytes means serializing every payload.
- **What leaves the heap does not leave the machine** (`payloadArchive.ts`). Past the in-memory window a payload is written to a store of its own in IndexedDB and the row keeps the ref; selecting the row fetches it back. Nothing about it is React state, which is the point — the working set is what a repaint walks, and the shelf is what the log can still reach. It is the one IndexedDB store `storage.ts` does **not** read into memory at startup.
  - **Keyed by an ordinal, not by the call.** Letting the oldest go is then one range delete rather than a list of keys held in memory, and a ref below the oldest one held is answered with nothing without a round trip. An index on the run is what takes a payload with its run — trimmed, cleared or discarded — because a row that is gone is a payload nothing can select.
  - **It holds the payloads of rows a session is holding, so it is emptied when a window opens.** The rows themselves do not survive a session, and keeping payloads under rows that no longer exist would be disk spent on nothing.
  - **A refused write makes room rather than giving up** — a quota is almost always what refuses one, so it lets the oldest half go and carries on. A row past the shelf says the same stated state it had before there was one.
- **Only the rows on screen are in the document.** Rows are a fixed height, so windowing is arithmetic and everything above and below is one spacer. A row takes values rather than an object so its memo holds.
- **The log follows the run like a terminal, and stops when you scroll.** The flag lives in a **ref**, because a run appends between two wheel events and a render-lagged answer would scroll the log back down under your hands. Pressing Run starts following again.
- **Runs are numbered, not named.** The number is the run's own (`Run.number`), because a position would renumber as old runs are trimmed. **A run states what it carried** (`Run.input`) beside the number, because Run repeats the last run's values, so the run on screen is the statement of what the next press will send; a blank value says `id=` rather than dropping the key, an empty string being a value a script reads.
- **The mark is the running indicator, in the log's tail bar and nowhere else** (`KajaTrace.tsx`). The logo is a trace, which is what a run is. **Not in the run pill** — the mark is three times the width of the status dot it would swap back to, so the pill's whole label would step sideways at the moment you are reading it. Everywhere the mark is not, the spinner still is.
- **Running is about the run, not a call** (`Group.running`). A script sleeping between two calls is still running, so `running` is a run with no duration that isn't stale; the in-flight count is what the strip and the payload machinery care about.
- **Two extra channels on every row.** The **loop key** is the identifying value read off the request — the only thing telling two hundred identical method names apart — and shares its field list with `draftTitle`. The **duration bar** is drawn against the slowest call in the run.
- **The log is never collapsed or summarised away.** The tail bar says what is out of sight rather than standing in for it.
- **A run says who pressed it, once there is more than one who** (`Run.origin`), and **a run that has nowhere to land is not kept** — which is almost nothing, since an agent's snippet has a draft.
- **A run keeps going when you navigate away**, so the sidebar row says so. Run/Stop in the command row tracks the *active* run, because Stop has to abort what it is showing.
- **Renaming or saving moves the console; deleting takes it with the file.**
- **A run's status is the worst status it contains** — there is no "partially succeeded". Items are ordered by start, never re-sorted, and keep their own durations; the run's duration is **wall time for the whole script**.
- **A new run always takes the console** (`followSelection`); everything short of one stays where it is put. Inside the run being watched the cursor follows the newest call, selecting one in flight when it is issued rather than when its response lands.
- **Live and last-time are different states.** Reopening a script gives its code and, if still held, its last run (`runStore.ts`) drawn faint; pressing Run replaces it in place. Retention is short because **expiry is a stated state, not a silent hole**: a run whose payloads are gone says so rather than showing an empty pane.
- **Copy is gone from the canvas** (a document of six block kinds has no coherent clipboard form); the Calls view keeps it, because a payload is one thing. Fold, unfold and copy sit on the payload pane's own row and exist exactly when the JSON viewer does.
- **Full-screen is a size, not a mode** (`Console.FullScreen`), which is why **all three views are shown at it**. The run keeps running behind it and the canvas's measure grows.
  - **Esc is the screen's only when nothing else wants it** — a focused ask field and a held call both `preventDefault` first, so the screen checks `defaultPrevented` before claiming it.
  - **The bar carries Run as the CommandRow's own element passed down**, rather than reimplemented, so the two can't disagree; and it carries the segmented control for the same reason it is a component — a size may not take two thirds of the run with it.
  - **Taking the screen settles the view as well as the size** (`enterFullScreen(view)`, the one door all four ways in go through) — without it the next run swaps the tab under you the moment it draws or doesn't. A call opened from the canvas or the stats is a change of view and nothing else, rather than dropping you out of the screen to read one row.
  - **It belongs to the run you were reading**: component state, not persisted, dropped when the file changes.
  - **A run nobody pressed Run for is presented rather than left in a panel.** `presentRun` is three states, unit-tested: a run that has drawn nothing **waits** for its first block, one that has drawn **presents**, and one that ended without drawing is **dropped**. One-shot — the console hands the request back once honoured.
  - **A run a click started keeps the size it was clicked at instead.** A deeplink presents because nothing about the window said a run was coming; a `kaja.run` cell is a person in a window they are already reading. The screen is taken at once rather than on the first block, since it is not being asked for. It crosses the file the click opens because that file and its run arrive in one paint: `runLinkedScript` opens the script itself, after the read, rather than leaving a second read to open it. **A panel is a size too**, so a click made at one is presented as a panel rather than as nothing — "a new run takes the console" is a rule the console can only apply to the file it was already on.

## The canvas is what a run drew

**A script says what it made, never how it looks.** The block set is closed and tiny (`blocks.ts`) — text, code, table, the asks, approve, perfTest — and that is the guard, not a starting point: the moment a script can paint pixels the console is a rendering engine. There is no `kaja.html`, no styling arguments, no layout control. Blocks stack in emission order; free 2D positioning would turn this into a quarter of work.

- **A table is a handle, because a loop is why tables exist here.** `kaja.table` returns something with `.row(...)`, and rows land one at a time so the canvas repaints as the loop runs. Blocks are recorded against their own id, so a block that fills in stays where it was emitted.
- **A row is a handle too**, with one verb: `.update(...cells)` — a row is declared when its work starts and rewritten when it finishes. The block is unchanged by any of it: `rows` is `string[][]` and an update is the same wholesale re-emit an append is. **A row is as wide as the table**: fewer cells draws blanks, and `.column(name)` widens rows already drawn. Renaming a column, removing a row and flashing a changed cell are all **out**. A handle into a table filled from a **source** goes quiet rather than throwing, since a restart makes it point at a row nobody is asking about.
- **A cell that is work says which kind of work it is** (`CellStatus`). A **promise** is work the script already started, so the table only waits; a **function** is work nobody has asked for yet, so the table asks — which is why one offers Retry and the other can't. An `Error`, thrown or returned, is a cell that stopped. Nothing in the signatures changed: `row(...cells: unknown[])` always accepted this.
  - **The row is drawn with everything it already has.** A waiting cell is the same bar a skeleton row draws, with no shimmer and no delay — it arrives *with* the row rather than replacing something.
  - **Drawn is what asks** (`pendingCells`): the canvas asks for every waiting cell it can see on every frame, so asking is idempotent and the table is what knows a cell was started. A **failed** cell is asked for only when someone asks, since retrying on sight is a loop. A bounded number are in flight at a time.
  - **A cell is addressed by where its row sits, not where it landed on the page** — arithmetic until a local filter takes rows out of the middle. Answers are checked against the row's **revision** on the way in, so a rewritten row and a restarted source both drop what was still coming. A block read back has lost its closures, so a waiting cell reads as `run to load`.
- **A cell can be a destination rather than a value** (`kaja.run`). It draws as a link and clicking it runs that script with those values, which is **the deeplink grammar said inside the window**: the same verb, the same name, the same query, resolved by the `isLinkedScript` both doors share. There is **no sheet in front of it**: the `arrived` door asks first because what is on the other side of a link may not be a person, and a click is one. Everything else about it is the deeplink's, so a cell reaches nothing a URL could not, and a draft is not reachable by either, having no name.
  - **It is the one cell that does not expire.** A live cell is a closure and reads back as `run to load`; a destination is a name and a map of text, which is storable.
  - **A destination is a name, so the editor is where it is checked** (`scriptRuns.ts`, read off the AST for `scriptInputs`' reason). Three answers around one rule, all resolving through the `isLinkedScript` the click resolves through, so none can disagree with what clicking does: the workspace's scripts are **offered inside the quotes**, a name that reaches nothing is **marked where it is written**, and an agent is told the same thing by `checkScript`. The mark is an error and **stops nothing**: a script is transpiled rather than compiled, which is what Run already does with a type error.
  - **And the parameters are checked by the compiler rather than by a second checker of Kaja's own** (`runInputDeclaration`). What a name is missing is a type to resolve against, so the folder is written out as one — a declaration file, because `moduleDetection: Force` makes every other file a module and what is wanted here is a global the kaja module can name. A key the script on the other end never reads is then TypeScript's own excess-property error. **Two answers are deliberately open**, because a false error here is worse than a missing one: a script nothing has read yet has no entry, and a script reading a key it doesn't name (a computed key, a `...rest`, the map handed somewhere whole) takes anything. A script that reads nothing is the one that refuses everything, and does it under a **name**, since an empty object type accepts every key rather than none and `never` prints as `never` where TypeScript prints an alias. A **value** is `unknown`: every one is sent as text.
  - **The folder is read as the editor asks about it** (`scriptParameters.ts`). A listing carries names rather than contents, so reading it whole at startup would be a request per file for an answer most are never asked for; `markRuns` is already the one pass that has read the destinations on screen. A write is told directly, a file that left the listing is forgotten with it, and a file that cannot be read is recorded as taking anything rather than left to be asked for again on the next keystroke.
  - **And a rename is followed into every destination** (`followScriptRenames`), the rule a renamed app is already followed under. A name that still resolves is left **exactly** as it was, so a file moved between folders keeps every bare-name link to it. A deeplink outside Kaja is what the address is meant to outlive and is not followed; a cell inside the workspace can be.
- **A table's rows are an iterable, and that is the whole of static-versus-live.** An array is one; so is an async generator, which only runs when something pulls it.
  - **The pager is over rows, not requests** (`tableView.ts`). Next means "the next page of rows, fetching if I have run out". The script never states a page size and never holds a cursor — the cursor is an ordinary local in its own loop.
  - **No lookahead.** Pulling one row past the page to light Next up would fetch a whole page to answer a question nobody asked, so an open source offers Next until it runs out. This is why the page clamp lets **one** page past the loaded rows through.
  - **`.total(count)` is how the script says how big the whole thing is**, said from inside the source's loop — a verb rather than an option because the count arrives *with* the first page, and on the handle rather than a second source parameter because arity there already means "restart me for each search". **A total is a claim and exhaustion is the truth**: a source that promised more and stopped has what it yielded. A restart clears it, and it is the one thing that spares the no-lookahead click.
  - **A live table's first page is pulled a microtask after it is drawn**, because a source reports its total through the handle the script is still assigning. The run still waits for it (`LiveTable.first`).
  - **Declaring the search parameter is what asks for the search text.** A source that takes one is restarted per search; one that doesn't is never restarted and the box filters the rows already loaded, saying so. A local filter **never** fetches. Arity is the switch because it is readable one line from the box.
  - **Paging moves nothing** (`holdsPage`). The frame keeps the height of a full page for as long as the table can page; only the final page of a table that can no longer page shrinks, and a local filter, being instant, is the one narrowing allowed to. **The old page stays, dimmed**, and it **stays on the click and dims on the delay** — a page cleared while the dim waits is the blink the wait exists to prevent. A first draw has nothing to dim, so it draws skeleton rows with widths fixed per column index; widths that re-roll every render look like activity that isn't there. **The toolbar states the page that was clicked**, not the rows in hand.
  - A column whose every non-empty cell is a number reads from the right, decided by the cells rather than by anything declared.
  - **A live table expires like a payload does.** The source is a closure and cannot be stored: read back, the table is the rows it had. **The usual way it expires is a reload nobody asked for** — WebKit drops the webview's content process after a sleep and Wails reloads the page — so a search the source took has nowhere to go and the box is **disabled and says `Run to search`** rather than taking text nothing answers; a local filter is over rows still here and stays.
  - **An agent sees one page** — nobody is there to press Next, so `run_script` reports `more: true`.
- **A call is not a block.** The body draws blocks and nothing else, in emission order. The run's calls are stated once, in the strip below.
- **A failed call does not interrupt the document if the script reported it.** The destructive row is drawn only for failures **nothing was drawn after** — a counter over everything in the run, against where it last drew. A run that fails and says nothing collects its failures at the end, one row per method with a way into the log.
- **A block that asks pauses the run.** `kaja.ask*` is drawn where it happened and the canvas stops there — the empty space under it *is* the pause. A dialogue is not a sixth block type; it is what a sequence of asks reads as. An answered ask collapses to a record, and a cancelled one says the script stopped there.
- **A block that approves is one of those, about a call that hasn't happened.** `kaja.approve(Shows.CreateShow({ … }))` draws the call and the request and parks the run: Approve sends it and hands back the response, Stop ends the script. It carries the request rather than a summary, because what makes a call worth approving is what is in it. **No button takes focus** — an ask focuses its input for free, but here Enter would send the request; `⏎` approves **this call only**, and the standing approval always costs a deliberate gesture. **Stop must not out-weigh Approve**: it is a refusal, not a catastrophe.
  - **The scope is the method**, because that is what the button can honestly say — all-methods would cover calls you have not seen. **The lifetime is the run**: `runScript` clears the approvals at the top of every run, both doors, and nothing about it is written to disk. **The script never learns of it**; the one place it is recorded is the block that granted it, so a run read back can say a decision was made once and used ten times.
  - A settled approve block is a record, not a control: it loses its amber and its payload and states the decision in one line.
- **A method hands back a `Call`, not a promise** (`kaja.ts`), which is what makes approval possible. **A call starts when it is awaited — or at the end of the tick, if nothing has claimed it**, so `await Shows.ListShows({})` sends immediately, a bare `Shows.Ping({})` still goes out, and `Promise.all([a(), b()])` still runs both at once (starting is idempotent). Claiming is a real operation rather than a matter of being first — `approve` calls `call.claim()` before its own first `await`, or the tick would end while the question was on screen and send the call itself. A call that has already gone out is **refused** rather than approved. Everything a call does happens when it starts, its log row included.
- **An ask asks for a kind of thing and hands that kind back**: `askStr`, `askInt`, `askSelect`, and no general `ask` beside them. `Str` rather than `String`/`Text` because `kaja.text` already means *draw a line*. The kind is on the **block**, because the canvas draws the control and checks the answer, and a stored run has to redraw its question. `ask.ts` holds that check, so the canvas, the fallback dialog and the value handed to the script are three readings of one rule. A select's answer travels as the **label** — what the canvas showed, and what a stored run reads back without its script.
- **A select is a listbox on the canvas, so it is typed into rather than opened**, and `⏎` is what answers, because a keystroke that answered would send the run somewhere on a typo.
- **The `kaja` object is flat** — `askStr`, not `ask.str`. It is met through the editor's completion list, where one `kaja.` shows every verb there is.
- **A run can be waiting on the tab you are not looking at**, which is the one problem splitting the views introduced. So a parked run says so three times before you can leave it and a fourth time once you have, on the sidebar row — as a ring rather than a spinner, which would say the script was working. The log stays readable throughout.
- **An ask with no canvas falls back to the dialog.** An agent's snippet is not that case — it has a draft. A question never answered is stored as cancelled.
- **Which view a run opens in** (`defaultView`): a run that drew something opens on its canvas, one that only made calls on its log. An explicit choice outranks that and sticks per file.

## Start

**Start is a view, and it is the one there is always a way back to** (`Start.tsx`). It is the permanent last entry of `views`: visiting it brings it to the front like anything else and leaving it lets it fall back down, but it never leaves the list, it sits outside the mounted cap so it never costs a real view its place, and it is an ordinary row in the finder. What it replaced was not a view — it was what the pane drew when `views` was empty, so the first thing you opened overwrote it for good. Nothing gains a close button: what "close" was wanted for is **back**, and back only failed because there was nothing underneath. It is recreated on every launch, so it is left out of the serialized views and put under whatever they restored.

**Nothing is opened for you any more.** A cold start used to open the first method of the first app as a draft, because the alternative was a blank pane; now there is somewhere to land, and which call you make is yours.

**Two screens, and which one is right is a question about the workspace rather than about the window.** With apps, the pane says **picking a method in the tree drafts you a script** — the whole model of the product, said nowhere else — then the last few things you were in. The people who see this screen most are not new, so it is a shortcut rather than an illustration; on a first run the recent list is **absent**, not an empty box. With no apps it is the cold start, naming the two doors into Kaja: adding an app is the filled button, because an agent is additive and cannot add one for you.

**The map is drawn here and nowhere else** (`KajaMap.tsx`): an agent on the left, Kaja in the middle, the four protocols on the right. This is the one screen with nothing else to say, so it is the one screen the whole flow belongs on; a second copy on the MCP page would be a picture the reader has already read. **Outside the app it is ported, never redrawn** — the website's hero and `docs/how-it-works.svg` are this file stroke for stroke, each in the palette its page has; the README's is one static SVG carrying a `prefers-color-scheme` block, because GitHub loads it as an image rather than as markup it can theme. A change here is a change in all three. The two actions sit under the ends the map already has, so a button lands where the eye is rather than in a row of its own.

## The command row and the finder

**There is no tab strip, and no open files either.** The pane shows one thing, and the window's right side opens with one **command row** (`CommandRow.tsx`): sidebar toggle, finder, the file's own pair, an action, the layout control. **Nothing else may be added to it**; new controls go on the sidebar's band, on a section header, or in the console header.

- **"Open" is not a concept** (`views.ts`). What is left is a **cache**: a bounded number of views kept mounted in most-recently-visited order so going back is instant and keeps its cursor. It has no UI and nothing can be closed out of it; a view holding edits that exist nowhere else (`holdsWork` — Variables, an app form) is never evicted, and Start is outside the cap entirely. `views[0]` is on screen; `views[1]` is what `⌘P⏎` returns to.
- **Preview tabs went with the strip** — `preview`, `keepTab`, `closeTab`, `⌘W`, row close buttons and close-confirmation are all gone. Navigating away keeps the mounted view as it is.
- **Kaja never starts on the compile log** — the log is a report on this session's apps, so starting there means starting on an account of a compilation that hasn't run. It starts on Start instead, and which of that view's two screens is right depends on the configuration, so **neither is shown until it has loaded**.
- **The finder** (`Finder.tsx`) is a combobox trigger over one list, and it is a **label first**: with the sidebar collapsed it is the only thing that says where you are. Typing narrows every group at once, which is what makes it the only surface that can search the calls. **`⌘P` is the only key that opens it**, on the previous place so `⌘P⏎` is "back"; a click on the trigger opens on the first row. Only opacity is animated — movement makes fast repeated `⌘P` feel unstable.
- **`⌘K` is deliberately unassigned.** It is the command-palette convention and a palette *does* things; this list only navigates, so the first thing anyone types into it is a verb. It is also a chord prefix in Monaco.
- **The action slot** — Run and the JSON toggle share one position, since a file is never both a script and a form. Run is absent (not disabled) on non-script surfaces.
- **The traffic lights move to the band, not the band to the lights** (`desktop/traffic_lights_darwin.m`). There is no position to set, so the title bar container is made as tall as the band and the buttons centred in it — public AppKit throughout, so it holds in the sandboxed App Store build. It is **re-applied rather than set once**, because AppKit re-runs its own layout on first show, on a title change (which kaja does on every run), on an appearance change and when fullscreen ends; setting a frame posts the notification this hangs off, so a reentrancy guard keeps the correction out of itself. **Fullscreen is left alone**: there the buttons belong to the menu bar overlay.
- **Split panes are cut, not deferred.** Splitting reintroduces "which one is current", the exact question removing the strip answered. Comparing responses is a console problem. (The layout control is not this: it decides whether the console sits beside the editor or under it.)

### The phone

**One breakpoint, at 640px** (`PHONE_QUERY`), and under it the window is a different frame rather than the desktop one squeezed: no sidebar, no splitters, no status bar. Above it the desktop frame is drawn unchanged, so an iPad in landscape is the desktop. Both frames draw the same view bodies — `renderBody` in `App.tsx` is the one place a view is turned into a body — and the editors are mounted once whichever frame holds them.

- **The finder is the whole of the navigation** (`PhoneFinder.tsx`). Its trigger is the header, which is the one thing that says where you are, and it opens as a sheet. With no query it is where you have been, **the app tree expanding in place**, and Kaja's own views; with a query it is the same ranked list the desktop finder gives, under the same `matchesDestination`. Bottom tabs, a drawer and a second search were each considered and cut, since each is a second navigation beside one that already goes everywhere. **What the status bar said is said on the rows**: the compile state and the MCP server's state are a dot and a word on their own rows in the Kaja section, so a row's `status` is the phone's status bar.
- **The console is the screen and the script is a sheet** (`PhoneFrame.tsx`, `CodeSheet.tsx`, `BottomSheet.tsx`). A run is what a phone is opened to read, so the canvas takes the body and the code sits along the bottom, a line at rest and two pages when pulled up: the code, and the log. **The log is the sheet's second page rather than a view of the console** — the console draws it there through a portal (`Console.phone`), which is what keeps one console rather than two subscribed to one file. A call picked off the canvas raises the sheet on the log; full screen is nothing more than the sheet getting out of the way.
- **The code is printed until Edit is pressed.** A page that opens a keyboard is a page you cannot read, so the sheet prints the buffer through the editor's own tokenizer and swaps the editor in on Edit. The editor is never unmounted for it, because the editor is the one the view cache holds. A file the server can't write has no Edit; its Run menu's `Duplicate as draft` is the way to a copy.
- **A file with no run opens on its code, and a run starting drops the sheet.** Only a live run: the runs a file kept from last time arrive settled and move nothing.
- **A sheet has two places to be and lands on one of them** (`snapSheet`): a flick decides by direction, a slow drag by the nearer end. Only the chrome drags, so the body keeps its own scroll.

### A key is the workspace's

`shortcuts.ts` is the one table of what the window answers to, and `shortcuts` in kaja.json is what a workspace disagreed with. It is **configuration rather than a preference of this machine**, which is what lets a kaja served to a browser ship its own keys and a checkout carry them — the same reason the variables live there.

- **The file holds overrides and nothing else.** An action nothing names keeps what kaja ships, so `Reset` is the row's entry being *removed* rather than the shipped chord being written into the file. An action named with an empty binding is one deliberately left without a key.
- **An override replaces the set rather than adding to it**, so what a row says is the whole of what that key does. Only Run ships two, because F5 is somebody else's key honoured beside kaja's own.
- **`Mod` is the platform's own command modifier**, which is why a chord recorded on one machine works on the other, and why a binding may not hold `Mod` and `Ctrl` at once. **The modifier set matches exactly**, which is what lets two chords over one key be two shortcuts; the handlers this replaced were each a hand-written `(metaKey || ctrlKey)` test that mostly forgot to say anything about Shift.
- **A binding is written in one canonical form** so equality is string equality, and a spelling nothing can be made of resolves to no binding rather than to a parse error — a hand-edited file cannot take a key away from the window.
- **A key is recorded, not typed.** A text field would be a grammar to learn for a value the keyboard can say itself. The recorder holds the keyboard in the capture phase while it is open, so a chord it is listening for is not also acted on behind it, and ⌥ on macOS is why an `event.key` that is not a letter or a digit falls back to `event.code`. A chord that cannot be one — a bare key, or one the host takes before the page is offered it — is refused with the reason rather than stored.
- **The chord you just pressed wins, and the row it came from loses its key**, with its revert standing so it is recoverable from its own row, and the row you were working in states what it took with an Undo in it. No dialog, because you asked for the key and the answer is reversible. Two rows may hold one chord where their scopes can't both be active, so the question is `scopesOverlap` rather than string equality, and it is asked at the moment a chord is recorded rather than carried as a state the screen reports forever.
- **The scope is a column, and it is stated on every row** from a closed set: an empty cell that means "global" is one you have to be told about, and two wordings for one scope read as two answers.
- **Zoom is not in the table.** It exists on the desktop to do what a browser already does with those keys, so a rebind would make the two builds disagree about keys nobody chose.
- **A label is a hook** (`useShortcutLabel`), because rebinding one has to redraw every place that names it. There are no shortcut string constants left.
- **The native menu states no accelerator.** macOS takes an accelerator before the webview ever sees the key, so a fixed one on File ▸ New Script is the one way the menu and the window could come to disagree. The window's own keydown is the whole of it.
- **A key for a verb the workspace hasn't got is not listed** (`listedShortcuts`) — the rule that takes Save as file off the command row rather than disabling it.
- **Reset all is the CommandRow's**, in the `action` slot every other view keeps its one view-level verb in, disabled rather than hidden while nothing differs: it is the answer to "can I get back?", which has to be readable before anything is broken.

## What Kaja failed at

The one error surface in the chrome (`appErrors.ts`, `ErrorStatus.tsx`), at the end of the footer's left group. Everything in Kaja auto-saves, so no screen has a save step and none of them says it saved; what a screen owes you is the news that a write **didn't** land, and that news is the same news wherever it comes from. So there is one place for it rather than a receipt per form.

- **The line is scope, and it is drawn already.** A script's console forwards to `deviceConsole` — the console as it was before `installUiLog` patched it — so a script's `console.error` reaches its run and never this store. The two things filtered are the notices that report no failure: a `ResizeObserver loop` notice is the spec saying it deferred the rest of its callbacks to the next frame, and a **cancellation** is the editor dropping work whose answer nobody wants any more, arriving as a rejection nobody is left to catch. The rule the other way round is the one to apply when writing new code: **a failure that already has a place is written to `deviceConsole`; a failure with nowhere else to go goes through the patched console and lands here.**
- **Errors only.** A warning is something Kaja carried on past, and counting them would light the footer in a session where nothing went wrong. It follows that a failure worth surfacing has to be reported *as* an error: a refused IndexedDB write is lost work, so `storage.ts` says `console.error`.
- **Absent until there is something to say.** A permanent `0` is a promise that a number is coming, and in most sessions it never does. It does not open itself either — an error arrives while you are working on something else, and a panel over that work interrupts more than a count in the corner does.
- **A repeat is one row that counts.** A render loop throwing the same error two hundred times has to collapse or the footer's number is a lie about how much is wrong. Collapsing is against the newest entry alone, so an interleaved error keeps its own row, and the message is compared whole, stack included. **The count is reports, not rows.**
- **Notification is coalesced to the frame** and the ring is capped, both for the reason the console store does it: an error storm arrives as fast as the loop throwing it. Recording runs *inside* `console.error`, so it must never throw and never log.
- **The popover draws a handful and the copy takes them all.** A list long enough to scroll is a log, and the place to read a log is wherever the copy is pasted. On the desktop kaja.log is the file a TestFlight user attaches to a bug report; on the web there is no such file, and the copy is it. The store is filled on both builds; only the write to kaja.log is the desktop's.

## Apps

**Everything is an app.** A gRPC or Twirp service is an app of type `"grpc"`/`"twirp"`; the built-in integrations `"openapi"`, `"openai"`, `"folder"`, `"mcp"` are apps too. There is a single `apps` list in `kaja.json`; a legacy top-level `projects` list is migrated on load.

`ConfigurationApp` is a `name` plus a typed `oneof app { … }`, so an app reads `{ "name": "…", "grpc": { … } }`. **The set field is the type**, two types can never be mixed (protojson rejects two oneof members), and each message declares exactly its own params. The server flattens the set variant's scalar fields to a `map[string]string` at the `OpenApp` boundary (`flattenApp` via protoreflect), excluding `headers`, which is forwarded per request rather than being a creation param. The experimental built-ins appear in the **New** dialog only under a feature preview. The type is fixed at creation.

### An import names an app

`import { Shows } from "theatre"` (`appImports.ts`). A module path follows the app only where the app declares one name in two of its modules and the app alone cannot say which is meant — which is the whole of what a path is for. Every app whose proto surface kaja generated has exactly one module, so a path there could never tell anything apart; an app built from proto files on disk has as many modules as you wrote.

- **One decision, in one function.** `moduleSpecifier` is what generated code, the finder's example and the MCP catalog all write; `resolve` is what the runner reads. A name is looked up in the app's modules minus the `.client` ones, which declare the transport's interface and are not a surface a script writes against.
- **Resolution is per name, not per import statement**, because one import may reach into two modules. A name nothing declares binds nothing rather than failing — that is an interface imported for its type.
- **The editor is told the same rule by a barrel** (`barrel`), a model re-exporting each module. `export *` drops a name two modules declare, so the editor refuses exactly what `resolve` calls ambiguous.

- **The map** — [docs/network-stack.md](docs/network-stack.md) draws every hop and how headers flow, per protocol, then traces one real call through each lane. Its "What never crosses which line" is executable: `server/pkg/router/traces_test.go` runs the whole lane against an upstream and asserts one bullet per case, so the doc and the invariants move together.
- **The client speaks gRPC-Web and nothing else.** Which protocol reaches an API is the server's business, so there is one browser transport, one framing and one out-of-band channel however an app talks upstream. An app the client would have to speak a second protocol to is an app the server invokes instead.
- **Contract** — `server/pkg/apps` defines `App` (factory), `Instance` (live, invocable) and a `Manager` (type registry + live instances). `App.Open` returns an `*Opened` describing the proto surface and the `Instance` its methods are invoked on; every app has one. **`Instance.Invoke` hands back a `Stream`** — the response messages, then the `Report` the call ends with — because a unary method is the stream that stops after one message, and that is what lets one contract carry every app and every kind of method. `apps.OneMessage` is the stream of a call that answers all at once, which is every app but the forwarded one.
- **An app is addressed by its own name.** `Manager.Open` registers the instance under it, replacing whatever was open under that name, and `Manager.Invoke` looks it up by it — the name the reserved header already carries. There is no target: nothing about where an app lives is handed to the client, and reopening one no longer leaves the last instance behind.
- **grpc is the one app that forwards rather than transcodes** — `server/pkg/apps/rpc`. Its `Instance` opens a `pkggrpc.ServerStream` at the upstream, so the request the client framed is the request the server gets, which is what carries a server stream through; the transport security rides on `apps.Call` because it is read from kaja.json when the call is made rather than held from Open.
- **twirp is an `Instance` with nothing to transcode** — a Twirp method is a POST of the request message, so the app posts the protobuf the client framed and hands back what came.
- **Open + compile** — the `OpenApp` RPC opens **every** app and returns the `proto_dir` to feed into `Compile`. The `Inspect*` RPCs are the only app-type-specific ones, and none of them creates anything.
- **Invoke** — there is one server-side lane: `internal/grpc.Serve` de-frames the request, calls an `Invoker`, and frames back however many messages arrive. `ApiService.InvokeApp` is that invoker and **the one door every call goes through** — it takes the app's name off the headers, expands their `${NAME}` references, applies the app's credential and transport, times the call and redacts what comes back.
- **UI** — `ui/src/apps.ts` models an app as a `ConfigurationApp` plus a runtime `target`. `ui/src/appTypes.ts` is the single registry of app types and bridges the typed oneof to the generic form: `appType` is the set field, `buildApp` constructs it, and its parameter keys are the generated camelCase field names. Each type's `icon` is how the app is shown everywhere it is named, and **every type's mark is its own** (asserted in `appTypes.test.ts`) — two types sharing one says nothing at all.
- **App settings** is a document identified by the app, and `</>` edits its content as JSON. Because the button belongs to the command row, the mode it selects belongs to the view and the "does it parse" flag belongs to `App.tsx`, which is what disables the way back. The JSON view opens on the **on-disk shape**, dropping a parameter the app doesn't set rather than writing an empty string.
- A type marked `customForm` renders its own body; its `parameters` list stays the contract with the config, and it reports what it read back as an `AppSurface`.
- **The name is a namespace, not a label**, so the name field shows the **import line the name produces** instead of explaining it — exact where the app's type fixes the path, and `…` where the app's protos decide it.

### Three of the custom forms share one shape

`GrpcForm`, `OpenApiForm` and `McpForm` all ask for **one thing** — where the server is, or which document — and everything after it is a choice between things that answer already declared. `OpenAiForm` is the fourth and shares none of it, because a chat endpoint declares nothing. All three:

- call their `Inspect*` RPC after typing stops (immediately for a picked file, an existing app, or ⏎) and discard all but the latest read;
- key that read on the address/document and **not** on credentials, which are typed a character at a time;
- carry every state — caption, reading, what was read, each classified failure — in **one slot** under the field, so nothing jumps, and let each failure **name its next move**;
- show nothing below the divider until something has been read;
- take a `${NAME}` variable in every text field, so a URL a variable can't be checked against is taken on trust and settled by the server;
- **derive** the app name rather than copying it, numbering a collision, and keep the pure parts in a unit-tested module beside the form.

### gRPC apps

- **The credential and transport are the app's, not the request's**, resolved in Go on the way out and never handed to the browser — which is what makes `"${secret}"` credentials work, and what makes Basic's base64 kaja's job. `GrpcApp` carries one credential and the transport the address can't state (`tls`, empty meaning read it off the URL, plus verification and certificate paths).
- **The reserved header is how the call finds its app.** The client sends `X-Kaja-App: <name>` beside the app's headers; the router pulls it back out before anything is forwarded and hands the name to `ApiService.AppConnection`, which reads the app out of kaja.json **at call time** — so replacing a token takes effect on the next call rather than the next compile. `apps.MergeMetadata` then applies the credential without touching a header the app configures under the same name (matched case-insensitively).
- **`grpc.TLSOptions` zero value reads the transport off the URL and verifies against the system roots**, which is what kaja always did, so a caller with nothing to configure passes it. `sharedConnection` keys the connection cache on the options as well as the target. Only `insecure_skip_verify` is genuinely unverified. Certificate paths are workspace-relative via `internal/workspace.Resolve`, the same rule as `proto_dir`.
- **`InspectGrpc`** reads the surface an app *would* be opened with without creating it, sending the credential (since a server that guards its methods usually guards the list) and reporting which reflection version and which transport answered. Failures come back as a classified `problem`. When the app leaves the transport to the URL a failure that *could* be the transport is retried the other way round; when the app pins it, the other is tried only to say "the server is there, but it only speaks TLS".
- In the form, **transport is stated rather than offered** once a server has answered, and the settled value is written into the app; only a server that didn't answer gets the choice. **Authentication** is a fixed list, because no document declares schemes, and each row states the metadata it becomes.

### Streaming, and what isn't supported yet

Server streaming works; client and bidirectional streaming don't, and the sentence for that is **"Client streaming is not supported by Kaja yet."** — naming the kind and nothing else, because everyone who reads it is somewhere different. `ui/src/streaming.ts` is the whole decision: `streamingKind`, `unsupportedReason` (the sentence, or `undefined`), and the code the refusal is labelled by.

**A gRPC app is the only one a stream can come back through**, because it is the only one whose calls are forwarded; every other app answers with one message. So `unsupportedReason` takes the app type too, and a streaming method on any other app is refused with the **app's own limit** rather than Kaja's, said without a "yet".

- **Listed, dimmed, marked.** Dropping the method would make the tree say the app has less than it does, so the row keeps its place with the sentence on it and the verbs that would call it omitted rather than disabled.
- **Clicking still writes the draft, with the sentence over the call.** The request is what the method takes, and reading it is why you clicked. The editor's own complaint — the method is not on the synthesized service — reads as kaja having lost it, so the comment says what is actually going on.
- **The run refuses before the transport does** (`client.ts`), which would describe itself where the limit is Kaja's. It is still a row: the script did make the call. `UNSUPPORTED` is the `FailureKind` no request can fix, which is why `classifyFailure` reads the code before the status.
- **Server streaming is called like any other method** and hands back the last message, with all of them in the log.
- **Go says the same thing in its own words**, on the split the MCP catalog is built under: the UI settles what the TypeScript is, `server/pkg/mcp` settles what to show. A mark added to one is a mark the other owes.

### A deprecated method is marked, not withheld

The API asking callers off a method says nothing about whether Kaja can make the call, so it is called like any other and the whole of the treatment is a mark on the name. It is the opposite half of the streaming refusal, and reads as one because of it: both are dimmed, and what says which is the refusal's `Ban` against a line through the name — Kaja won't, against the API would rather you didn't. What says the call still goes out is the row keeping its verbs.

**One channel, whatever the app**: `@deprecated` on the generated client interface's method. protoc-gen-kaja writes it for `option deprecated = true`, and an OpenAPI operation's `deprecated: true` becomes that option, so `isDeprecated` reads the tag off the JSDoc and nothing downstream asks which kind of app the method came from. A **method** is the only thing carrying it. The sentence is `Deprecated by the API.` and nothing more — naming who decided is the one thing a strikethrough leaves open. Go marks it too, on the split above.

### OpenAPI apps

`server/pkg/apps/openapi` reads the spec (JSON or YAML) from `spec_url` or inline `spec_content`, generates one `.proto` plus a per-method HTTP binding manifest, and compiles it with the embedded protoc-go. The upstream base URL comes from the spec's `servers` unless `base_url` overrides it; an **uploaded spec has no document URL**, so it must declare an absolute server or supply `base_url`. Every generated field carries `[json_name = "<openApiName>"]` so proto3-JSON keys match the REST shape. `Invoke` decodes with `dynamicpb`+`protojson`, transcodes to and from REST, then re-encodes.

- Both 3.0 (`nullable: true`) and 3.1 are handled, and **3.1 spells nullable two ways, so both are reduced to the type itself**. Left in, a null variant makes every nullable scalar look like a union of mixed categories and decode through `Value`, and every nullable `$ref` look like a union needing a message of its own.
- **Composition is resolved**: `allOf` merges into the message's fields; a `oneOf`/`anyOf` whose variants are all objects merges into one superset message; a mixed-shape union models its first variant.
- **A response member the document mis-declares is dropped like one it never declares.** The decode is strict first; when it fails, the members whose values cannot be read into their fields are pruned (`pruneMismatched`, judged by protojson itself) and the rest is read — a live API drifts from its document field by field, and one drifted field must not take the response with it. Only a body that still cannot decode is reported as unreadable.
- Query parameters honour `style`/`explode`.
- **`testdata/kitchensink.yaml` exercises all of this and must generate and compile cleanly end to end. Extend it when adding schema features.**

**A name is read inside its scope, so it never repeats it.** Operations are grouped into services by their first tag, and a spec that namespaces its own identifiers used to say the same word three times. Two trims cut that, and both are guarded so a spec that isn't repeating itself generates exactly what it did before.

- **A namespace every namespaced tag and operationId shares is the API naming itself**, which the app's name already does once at the import, so it is stripped from both. It is the whole leading dot-segment or nothing: one identifier disagreeing means the segment is telling them apart, and fewer than two namespaced identifiers is not a convention.
- **A method drops its service's name from its front**, because the service is the scope it is read in. Prefix only, at a word boundary — an operationId that merely *contains* the resource is left whole rather than cut at a guess.
- **A method name is unique within its service; a message name is unique across the file.** So the messages an operation generates hang off its untrimmed name rather than off the short method name — two services both declaring `Get` must not collide.

**The HTTP envelope.** Carrying HTTP inside gRPC needs somewhere to put the parts protobuf has no shape for, and the rule is that the envelope exists only where it is unavoidable. An operation whose only input is an object body **is** that body. An envelope field appears only when the payload can't be the message: a body beside path/query/header parameters, a body that is an array, and every non-object response. Those fields carry `(kaja.http_payload)`, declared in `apps/openapi/http.proto`, which the app writes into the proto directory. The mark survives into the generated TypeScript, which is how the client tells an envelope from a property an API happens to call `items` (`ui/src/httpEnvelope.ts`): a message that is **nothing but** a marked field is an envelope, and the console shows the payload instead. **Only the response is unwrapped, and only for display** — the wire and the generated types are untouched, so a script still reads `response.items`.

`kaja/http.proto` carries four more marks, for the same reason: the HTTP request line on every method (the verb is the only thing saying whether it reads or writes), and where a field goes, whether it is required, and what an enum declares. proto3 has no `required`, so without it every field looks equally optional.

**A document's enum is carried beside the field, not modeled as a proto enum.** A proto enum value is an identifier, so a lowercase value would go on the wire misspelled unless it happened to be spelled the way proto spells one — and a closed type would refuse a state the API grew after the document was written. So the field stays a `string` and the mark lists what the document declares. The set is read through a `$ref` and an `allOf` wrapper, off an array's `items`, and across a union **only when every variant declares one** — one open-ended variant means the field takes more than the union lists, and a set that is not the whole truth is worse than none. Only strings are carried, and a set past a cap is dropped whole rather than cut short. The values reach the UI on `FieldInfo.options`: folded into the JSDoc for an agent, and offered inside the quotes in the editor, which is the Swagger UI select an OpenAPI app otherwise loses.

Header parameters are ordinary request fields whose `json_name` is the header name; `transcode` sets them **after** the app's configured headers, so a value typed for one call outranks one configured for every call.

**Auth** (`auth.go`) resolves the spec's `securitySchemes`/`security` into an `auth` that injects the credentials the way the scheme expects. `components.securitySchemes` keeps declaration order through an `UnmarshalJSON` of its own, a JSON object being unordered to a decoder, so the form's preselection is stable. `security_scheme` pins which scheme the credentials belong to (or `"none"`); the form always writes it. An empty value honours the document-level `security`, else the sole declared scheme, else falls back on the credentials given. Spec auth is applied before any per-request header. A document behind a login is fetched with its own header, kept apart from the API's own credentials because they are usually different tokens.

**In the form**, the server section adapts to `servers` — one is stated, several become a radio list, placeholders become selects or inputs — and the choice is written out as `base_url` and matched back when the app is edited. **A scheme row is labelled by where the credential goes, not by the type the document gives it**: an `apiKey` scheme is `Header X-API-KEY` or `Cookie __session`, never "API key" — that is also what an API calls the credential its dashboard hands you, so a row wearing it is read as the one that takes it, and a document declaring a session cookie beside a bearer token sent the key to the wrong place. The name is derived from the title by dropping the words that describe a document and joining the rest in PascalCase; a title that is nothing but those words keeps them.

### Chat app

`server/pkg/apps/openai` calls a chat model, and **`api` says which one**: OpenAI chat completions or the Claude Messages API. A gateway serves either at whatever path it likes, and the two differ in the request body, the response and the credential's header — three things an endpoint cannot settle. The proto surface is the same either way, so swapping one app for the other leaves a script working. `wire.go` is that pair of translations and nothing else.

- **The credential is the app's**, resolved in Go and never handed to the browser. **An empty `auth` is whichever credential the API's own dashboard hands you**, which is the whole of why the app used to fail against the Claude API. What an API insists on (`anthropic-version`) goes on **before** the app's own headers, so a header configured under the same name outranks it.
- **A response the wire can't read is reported, not passed off as an empty reply.** Each wire names the answer it wanted, which is the whole diagnosis when an endpoint speaks the other API; the Claude wire has to check `type` to notice at all, since every other field of a Message is optional to a JSON decoder.
- **The form is the custom form with nothing to read.** It calls no `Inspect*` RPC and settles at the first call. Picking a row writes `api`, `endpoint` and `auth` together, the endpoint staying editable, and `matchApiChoice` reads an app back onto the row that would have written it.
- **The config key stays `openai`** — it is what every `kaja.json` that has one already says — while the label is **Chat**.

### Folder app

`server/pkg/apps/folder` binds to one folder on disk and serves four operations: list, create, read, append. It writes a static proto source out, compiles it, and dispatches by method name. **It knows nothing about file formats** — content is written and read verbatim. It is local, so it forwards no headers and reports no upstream ones.

- **Every path it reports can be handed straight back to another method**: relative to the app's folder, slash-separated, with nothing to join first. That invariant is what makes the app usable one method at a time.
- **The boundary is `os.Root`**, which enforces the folder at the syscall level, symlinks included. The lexical check in front of it is not the fence.
- **A write creates the folders its path implies**, which is what keeps the app at four methods — no `CreateFolder`, no `mkdir` flag.
- **The listing is breadth-first and capped**, so a truncated listing is the top of the tree and says so. Nothing is filtered, `.git` included, and entries are sorted per folder because the filesystem's own order is not one.
- **One word the whole way down**: the type is `folder`, the service `Folder`, the method `ListFolder({ folder })` — the app is a place somebody picked. It stayed one service because a service name becomes a `new Function` parameter in `scriptRunner.ts` and `File` would shadow the DOM global in every script.
- **The folder is picked on the desktop, not typed.** macOS grants a sandboxed app a folder by the user choosing it, so a typed path has no access at all, however valid it looks. `picked` on an `AppParameterDefinition` is that rule. `proto_dir` and the certificate paths are not picked: they are workspace-relative, and the workspace is the one folder the app already holds.

### MCP app

`server/pkg/apps/mcp` is an MCP **client**: it connects to somebody else's MCP server and renders what it exposes as a proto surface. (Not kaja's own MCP server below, which points the other way. They share a name and nothing else.)

- **A tool is a method and its input schema is the request.** Each tool's `inputSchema` becomes the request message, field per property, **in the order the document declares them** — sorting would renumber the message the moment a tool gains a property. Every field carries the property's own name as `json_name`, so the message *is* the arguments object and `invoke.go` needs no mapping table. Prompts become methods of a `Prompts` service; resources get three fixed methods, since a resource is addressed by URI. Only the kinds a server exposes are emitted.
- **What JSON Schema leaves open stays open.** Nested objects and `$defs` become messages (the name is allocated before the fields are walked, which is what terminates a self-referential schema; the pointer it is remembered under belongs to the one document being walked, since every tool declares its own `#/$defs/Item` and two of them are two shapes), `allOf` and an all-object union merge, and `additionalProperties` with a schema is a map. Everything else is `google.protobuf.Value`. proto3 has no `required` and no place for an `enum`'s values, so both go in the field's leading comment and reach the editor as JSDoc.
- **A tool result is a result, and the client reads its verdict.** A tool reporting `isError: true` comes back as an ordinary response, and `client.ts` reports the call as failed on the way through (`TOOL_ERROR`), the way a fetch's non-2xx is reported: the row is red, the response tab shows what the tool returned, and the script is handed the response. Go says nothing about it, because the exchange succeeded. A JSON-RPC error is the server refusing the call it received, so it is shaped as a refused call (`apps.NewRefusedCall`): the exchange's own status, the error's code in the words the specification reserves, and the error object as the body. An HTTP failure is an `apps.UpstreamError`, and a result asking the client for something back (sampling, elicitation, roots) says so rather than arriving empty, because kaja declares none of those capabilities.
- **Every field read off a document is `optional`**, required ones included, as is the static `Content`. Presence is what lets a zero the script wrote reach the server and keeps a field the server left out from being drawn as its zero — and a *required* field is the one that must carry it, since `0`, `false` and `""` are values a required field is most often set to and a field without presence drops all three. What the document insists on is said in the field's comment, which is the only place proto3 has for it. A JSON `integer` is a `double`: it has no size, an id or a timestamp overflows int32, and int64 would reach the script as a string. A `type` naming two types is a `Value`.
- **A session a legacy server has forgotten is opened again, once** (`sessionLost`). The specification says so with a 404 and the reference server with a 400 naming the session, and both put a JSON-RPC error under the status, so the status is read off the error rather than off a bare failure. Every stateful server does this on restart, and the stdio bridges above all.
- **A call carries a `progressToken`**, because a server sends progress only to a caller that asked; a listing carries none. **The response is the end of what is read**: a server that keeps the stream open for keep-alives would otherwise hold the call until it timed out.
- **The client is dual-era, and that is the whole of `client.go`.** The revision that dropped the `initialize` handshake carries version, identity and capabilities on every request, with no session; everything before it opens with `initialize` and may pin a session id. Which one a server speaks is settled **once**, by sending `server/discover`: only the error the modern revision defines identifies a modern server, and **anything else at all** is the handshake era, because a server from before the split has no way to say so. A response arrives as a JSON object or as an SSE stream whose last data event is the response.
- **A parameter the server annotated is mirrored into a header** (`header_params.go`). `x-mcp-header` names the `Mcp-Param-{Name}` an argument's value travels under so an intermediary can route on it without parsing the body, and it is read where the tools are listed rather than on every call: a tool carries the name and the chain of `properties` keys reaching the value. **An annotation anywhere it cannot be extracted from invalidates the tool**, which is why the check is a walk of the whole document — under `items`, a composition keyword or `$defs` it names a value the client cannot read, and a header an intermediary routes on that the body disagrees with is worse than a tool nobody is offered. Such a tool is left out of the listing and said so in the compile log, so one mis-annotated tool doesn't take the rest with it. The headers are the modern transport's; a handshake-era server is sent none.
- **What the server says while it is working is the call's, not the log's.** Progress and log notifications arrive on the response stream ahead of the response, and they ride back as lines on `apps.Report.Notices` — the Headers view states them between the two halves, where they happened. They are capped where they are read and dropped with the headers when the trailer won't carry the whole report, so a server logging in a loop can't push the failure out of it.
- **The credential is the app's** — bearer by default, MCP's authorization framework being OAuth — resolved in Go so a `"${secret}"` token never reaches the browser. It is asked for **per request** rather than held from Open, because a token that renews itself has to reach the next call without the app being reopened.
- **Streamable HTTP only.** A stdio server is a subprocess and the app contract has no place for one; the transport is behind `Client`, which is where that would go. The older HTTP+SSE transport isn't spoken either, but it is recognised: an endpoint that refuses the POST and answers a GET with an `endpoint` event is that transport, and the form says so instead of saying nothing serves MCP there.
- **An endpoint naming a variable this kaja doesn't define is readable elsewhere.** `Inspect` says which name is undefined and the form still lets the app be added, under a name of the person's own, since the app is read where it opens.
- **The form's default credential is none**, because the read that filled it sent none; a token with no scheme beside it is a bearer token, which is what the server reads it as.

#### The servers kaja is set up for

`ui/src/knownServers.ts` is the list the MCP endpoint field offers, and it is what makes an app out of a name somebody half-remembers. An entry is a name, an endpoint and a mark, and it exists exactly where signing in is something kaja can carry through knowing nothing but the address. **A bundled client id is one way to be that and not the point of the list**: a server that registers a client on demand needs nothing shipped for it at all, and `clientFor` reaches the same place either way, so `oauth_clients.go` holds only the servers that register nobody. That is what the row's `sign-in ready` says, so a server kaja is **not** set up for does not belong on the list rather than belonging on it quietly.

- **The match is on the endpoint, never on the name.** An entry is a URL, so matching one is exact — canonical scheme and host, no default port, no fragment, no trailing slash, the rule a token is already kept under. Nothing is guessed from what a server calls itself, there is nothing to match before the server has answered, and an address that is a `${VARIABLE}` or a localhost port simply isn't one of them.
- **Taking a row is the address and the credential at once.** An entry exists because kaja can sign in to it, so picking one writes `oauth` over the bearer token a 401 would otherwise select; pasting the same URL by hand is read the same way.
- **A prefill is a starting point, never a lock.** Editing the endpoint drops the whole of it, the other credentials stay selectable, and the OAuth fields are behind `Use my own client ID` with `Back to Kaja's` returning — a client id or a scope already in the app is that ask having been made before, so an app configured by hand opens on its own fields.
- **Recognition is said twice and adds nothing twice**: a chip in the field, and the pill on the credential row it changed. Neither is a state — both are read off the endpoint on every render.

#### Signing in

`auth: "oauth"` is the credential nobody types: kaja runs MCP's authorization flow and keeps what the authorization server issued (`oauth.go`, `oauth_flow.go`, `oauth_store.go`).

- **The token is never in kaja.json.** The configuration file names a workspace's apps and is meant to be committed, and a token that renews itself is not something a person could keep in a file of theirs anyway. It goes in the platform's own state directory for this installation, keyed by the **canonical resource URI** — the endpoint with its scheme and host lowercased, its default port and fragment dropped, no trailing slash — because that is what a token is issued for and the only address it may be sent to.
- **Signing in is a write, so a read-only workspace hasn't got it.** `NewApiService` builds no authorizer where the configuration can't be updated, and `AuthorizeMcp` says so rather than opening a listener nobody could reach: the browser signing in is on the machine kaja is serving from, which a deployed kaja's visitor is not.
- **The redirect is a loopback listener of kaja's own**, on a fixed port beside the ones it already holds — **any free port where that one is taken**, because an authorization server matching a loopback redirect ignores its port (RFC 8252), so a port something else is holding is not a sign-in that cannot happen. It is opened when a sign-in starts and closed when the last one settles. It is not a page of kaja's: the desktop's window is served from `wails://`, which no authorization server would accept, and a deployed kaja is somewhere else entirely from the browser. One address means one registration that goes on working, the port not being part of what is matched.
- **`AuthorizeMcp` streams because the flow has a browser in the middle of it.** The page to open goes out first and on its own, since nothing can happen until somebody opens it; the verdict follows. **The window opens the URL**, the desktop and a browser differing in how. What travels with it is a `SignInPrompt` rather than a URL, because the device grant has a code to state beside the page.
- **A server that refuses a public client is signed in to with the device grant instead** (`oauth_device.go`). GitHub draws no line between a public client and a confidential one, so it refuses the code exchange without a `client_secret` however the request was proved — and a secret is the one thing kaja may not ship. The device grant asks for none. It is a fact about the **server**, so it is recorded beside the client id kaja ships for that server and a client id of the person's own takes the same route: the refusal is the token endpoint's, whoever is asking. What changes above it is that the person carries the code across instead of the browser carrying an answer back, so there is no loopback listener and the prompt has a `user_code` in it; a server advertising a device endpoint is not reason enough on its own, the redirect flow being the one that asks nothing of the person.
- **A refusal is read out of the token endpoint's answer whatever its status.** GitHub answers 200 with the error in it, and RFC 8628's `authorization_pending` arrives the same way, so reading the status first reported a refusal as an answer that was missing a token. Only `authorization_pending` and `slow_down` are worth asking again after; everything else is a refusal repeated.
- **kaja registers itself only where it has to.** A client id the person already has outranks everything — which is also how a client ID metadata document is used, that being an https URL somebody hosts, and kaja hosts none — then one kaja ships for that server (`oauth_clients.go`), then one this installation registered with this server before, then one registered now. **What kaja ships is a public name rather than a credential**: a server that registers nobody and reads no client ID metadata document leaves a hand-registered client as the only way in, so kaja registered one instead of asking each person to, and it sits in the source where a redirect URI already does. What kaja ships outranks what it registered, because anything held against such a server was registered before there was an id to ship. A registration belongs to the issuer that made it and is kept against it; signing out drops the token and leaves the registration, which is this installation's record with that server rather than this sign-in's. **A renewal presents the client the token was issued to**, which is why the grant carries it: neither a configured client nor a shipped one is in the store, so a refresh that went looking there sent no client id at all.
- **A server publishing no resource metadata is signed in to at its own origin.** That is what an MCP server was before RFC 9728, and metadata served by the host the endpoint is on is the server's own word exactly as the missing document would have been - so a `.well-known` that answers 404 is not a server nobody can sign in to. A document found at the root **about the root** is passed over on the same rule: a host may serve several endpoints, and a document about another resource is not this one's. What is reported when the origin has nothing either is the missing resource metadata, that being the document the specification asks this server for.
- **The authorization server's own metadata is checked against the address it was fetched from**, and an `iss` that comes back is compared to the issuer recorded before the browser was opened — including on an error response, which is refused before it is repeated. Those two, with PKCE and the `resource` on every request, are the whole of what keeps one server from spending a token at another.

### Upstream errors

**An app that speaks HTTP reports the HTTP call it made, and models none of it in its own proto.** When an upstream call fails with HTTP >= 400, `Invoke` returns a structured `apps.UpstreamError` — status, a human message extracted from the body (RFC 7807, Twirp's shape, and the common `message`/`error` envelopes), and the raw body. **A failed HTTP call is shown as an HTTP failure, not as the gRPC error it was tunnelled through.** `Serve` maps the failure to the closest gRPC status for any plain gRPC-Web client but sends the whole thing in the `kaja-upstream` trailer, which `client.ts` uses **in place of** the `RpcError`. Nothing of the tunnel reaches the response tab, and a genuine gRPC failure keeps its `code`.

**But that envelope is the carrier, not the failure** — the response tab shows the `body` alone (`unwrapFailure`). Everything around it is stated elsewhere: the status on the status line, the request line on the Headers view, the extracted `message` **only** when the body is empty. Recognising one is structural (`asUpstreamFailure`: an HTTP status and a request line, which a gRPC failure has neither of), so a stored run displays the same as a live one, and only the display changes — the error object keeps its fields, which is what a script catches and what `classifyFailure` reads.

**A response the app cannot read is reported the same way** (`NewUnreadableResponse`). An endpoint that answers 200 with something other than what the app's methods return used to arrive as a bare decode error, which names neither the call nor what came back. Two things follow from the API having answered: the message is the app's reading of that answer rather than a summary lifted out of it, so **both are shown**, and the status is named `responseStatus` rather than `status`, which the client reads as an HTTP failure. The lane still has to map a status, which is what `TransportStatus()` is — 502, kaja failing as the gateway it is here — never the status anyone is shown.

**The gRPC lane is a stream, and every call takes it.** Nothing at that end of the wire tells a unary call from a server-streaming one — the request framing is identical, and a unary method answers with the one message and the status that a stream of one is — so the grpc app opens a `pkggrpc.ServerStream` for everything and `Serve` forwards however many messages arrive. **Both directions are binary frames** (`application/grpc-web+proto`), never the base64 `grpc-web-text` protobuf-ts defaults to: a text body is one continuous base64 stream, so a frame whose bytes miss a group boundary holds its last two back until something follows them — on a stream, a message held until the next message — and going out it is a third more bytes for nothing. So there is one frame parser and no text branch to keep working. And the call lives as long as the browser's request rather than a deadline of Kaja's own, which is what makes a long stream possible and what carries Stop through to the upstream.

**Trailer encoding.** Every gRPC-Web trailer `grpcWebResponse` emits, `grpc-message` included, is percent-encoded. gRPC-Web trailers are a text block clients split on CRLF and read as Latin-1, so unescaped UTF-8 arrives mangled and a newline would end the line early. protobuf-ts does not decode `grpc-message`, so `client.ts` does.

**The Headers view is the exchange, in two halves**, and it is always the API's own headers: the upstream ones where Kaja carried the call, the transport's where the browser called the API directly and they *are* that exchange. The gRPC lane is that second case even with Kaja in the path — it forwards the same call rather than transcoding one, so the server's own metadata comes back as the response's headers rather than as a hop of its own. The browser-to-Kaja hop is not what a call is read for.

- **The group bars are the strip, which is why this is the one tab without one**, and the rule is that **the strip describes the pane in front of you** — so Request loses the status and the duration it was borrowing (a request has no status, and the outcome is stated on the row directly above), and Response keeps them, where the body *is* the 401 and the number is the key to reading it.
- **The status appears once, beside the headers it came with** (`exchangeStatus`), carrying the code and the **reason phrase**, which the other two tabs have no room for and which is what makes this tab worth opening. It is the *exchange's* status rather than the call's, so a response Kaja could not read states the 200 it arrived with; the row above is what says the call failed. An app that speaks no HTTP has no status line. Duration and bytes sit outside the pill because they aren't protocol — they're ours.
- **A call that succeeded has a request line and a status too, and nothing else recorded them.** A failure always carried both on its `UpstreamError`; `apps.Report` now carries the same three so the trailer reports them whatever happened. A fetch fills them in itself — the browser made that call.
- **One key column, measured across both halves**, so a value starts at the same x in the request and the response and the column doesn't jump between calls. **Long values wrap with a hanging indent** rather than truncating: a traceparent or a `Set-Cookie` is exactly the thing the tab was opened to read.
- **Names as they were given, in the order they arrived.** Nothing is alphabetised: the log's job is to be complete, and reordering is editorialising.
- **A call with no response yet keeps its response bar with a pending dot and nothing under it.** The half exists; a placeholder would be stating something nobody sent.

**Upstream timing.** Every call the Go process carries reports the upstream exchange it made, in milliseconds it measured itself, and **the client shows it as the call's duration everywhere one is shown** (`callDurationMs`: the upstream time when Kaja measured it, the whole round trip when nothing did). Both durations stay on the `MethodCall`, so the summary's hover carries the breakdown; the run's wall time stays client-observed.

**`kaja-upstream` is one trailer holding one object** (`apps.Upstream`): the exchange an app made — its request line, the status it was answered with, and the headers both ways — the duration, and the failure. It is the response-side counterpart of `X-Kaja-App` — Kaja's own out-of-band channel, consumed at the one boundary (`absorbReserved`) and never shown as a response header. Four names meant four values to escape, four to parse and four passes of the trailer block's budget; one object is written once and read once. The budget's promise survives the merge: a report too big to carry is written again **without** the headers that merely describe the hop, so the failure itself still gets through.

## A fetch is a call

**Not everything worth calling is an app, and `fetch` is what a script reaches for when it isn't** — a webhook, a health check, an API nobody has configured. It was already being written; what it was not was visible. So it is Kaja's: `runFetch` (`kaja.ts`, over `fetchCall.ts`) is the standard `fetch`, and inside a script body the bare name is bound to it the way `console` is, so there is no unrecorded request a script can make.

- **`fetch` is the only spelling, and there is no `kaja.fetch`.** A verb on the `kaja` object beside the global would be a second name for one function — the same reason there is no `kaja.log`. So the implementation is a function taking the run's `Kaja`, never a method on it.
- **It is the standard API on purpose.** The signature is `fetch`'s and so is the `Response`, because everyone who writes a script — every agent above all — already knows it. Nothing is renamed and nothing is added: what changes is that the call is recorded.
- **What it hands back is a `Call<Response>`**, which is what makes `kaja.approve(fetch(url, { method: "DELETE" }))` possible: a call starts when it is awaited, so awaiting it is fetch and holding it is approval.
- **A fetch is named by its verb and its host, and keyed by its path** (`callLabel`, `callKey`). Same two channels as a service call, same row. `callLabel` is the one definition — the log, the strip, the stats table, a failure notice and the agent's run report all read it.
- **`http` on the `MethodCall` is what makes one a fetch** wherever a call is read back, a stored run included. `service` and `method` are filled with the host and the verb so nothing downstream has to ask, and the tree ledger is the one place that checks: a fetch has no node to open.
- **A non-2xx is reported as a failure and handed back as a response.** The error is shaped as an `UpstreamFailure` because that is what it is, so the row, the response tab and the Headers view all work through machinery that already existed. The script still gets the `Response`, with `ok` false, because that is fetch. A request that never completed **throws**, also because that is fetch: a script that wrote a `try`/`catch` is written against that contract, and this is the one place Kaja's "a failed call is reported, never thrown" gives way to the API it borrowed.
- **The budget is the host's** (`kaja.rateLimit("api.example.com")`), which is what a fetch has instead of an app. That is the only thing a rate limiter may be named by rather than handed: a host is written in the URL, so there is nothing to point at.
- **Who makes the call is the one thing that differs between the builds** (`fetchTransport.ts`). On the **web** the browser makes it, so a fetch reaches exactly what a page can reach: an API sending no CORS headers needs an app. Routing that through Go would make a deployed kaja a proxy for arbitrary URLs, which it must not be. On the **desktop** the page can reach nothing at all: it is served from `wails://`, which WebKit reads as an insecure, opaque origin, so an https request fails before it is sent under an origin no API could allow. The process behind that webview is the machine the script is already running on, so it makes the call, on a lane mounted in `webviewHandler` rather than in `router.Mount` — which is the whole of what keeps the web's rule the web's. Either way a `${NAME}` in a header is not resolved.
- **`X-Kaja-Fetch-*` is that lane's own channel**, the fetch's counterpart of `X-Kaja-App`: the target on the way out, and on the way back the URL the response was finally read from or the failure where there was no response. It is read at the one boundary and never shown as a response header, and stripped from what upstream sent before anything is copied, so an API cannot write it. **Only the error header is a request that never completed** — a status the API answered with is a response and comes back as one, so the same non-2xx machinery reads it on either build.
- **The response is read once and handed over again** (`holdResponse`): the log has to hold the body and a body can only be consumed once, so the script gets a `Response` over the same bytes. It is why a streamed response is the one thing a script's `fetch` does not carry, and why an oversized or non-text body is described rather than kept.
- **Everything else follows from the call being ordinary.** It is a row the moment it is issued, the run's signal aborts it, it counts in the stats and in a `kaja.perfTest`, and its request and response reach an agent in the run report — none of which needed a second path.

## The globals a script sees

`scriptGlobals.ts` is the one answer to "what is in scope in a script body that its imports did not put there", and it has three groups. The bindings are parameters of the `new Function` wrapper, which is what makes them the script's without touching the page's own.

- **Bound to the run: `console` and `fetch`.** Both are the standard API under the standard name, and Kaja adds no name of its own for either. Being the run's is what Kaja adds, and it changes nothing about what is written.
- **Filled in: `crypto`.** `randomUUID` is a secure-context API and neither the desktop's `wails://` page nor a kaja served over plain http is one. The script's `crypto` is a clone of the page's with `randomUUID` always defined. Cloned rather than patched: a script must not be able to change what a compilation or a call mints ids with.
- **Refused: the globals that cannot work here.** Each is bound to a proxy that throws a sentence naming what to reach for instead — a property, a call and a construction alike, so `process.env`, `require("axios")` and `new XMLHttpRequest()` are all answered where they are written rather than failing further on. `prompt`/`alert`/`confirm` did nothing at all before this, which is the worst of the three ways to fail.
- **A binding of the script's own always wins**, for every name: an import or a `const` named `document` is a name the author chose, and shadowing it would be kaja taking a word it does not own.
- **`REFUSED_GLOBALS` is one table, read twice** — bound here, and printed into the `kaja` module's header, which is what Monaco checks a script against and what an agent gets from `describe_type "kaja"`. A list an agent reads and a list the runtime enforces have to be one list, or the one an agent reads is the one that rots.
- **It is a signpost, not a sandbox.** `globalThis` and `Function("return this")()` reach the real page and are not closed off. A script is code the person whose Kaja this is chose to run; the value is in what a script that reached for the wrong thing is *told*. The bar for adding a name is that the global genuinely cannot work here — not that a script has no business with it.
- **`bindMembers`** is what both the console wrapper and the crypto clone are built with: console methods sit on the prototype in some engines and on the instance in others, and are enumerable in neither.

## Variables

The `variables` map in `kaja.json` is read by scripts as `kaja.variables.<name>` and by app configuration through `${NAME}` expansion, including inside longer values. A variable's value either **is** the value or names the source that holds it outside the file: `"${secret}"` (the OS keychain, else `KAJA_<NAME>` in the environment) or `"${env:X}"`. "Secret" is not a kind of variable — one list, one namespace, one syntax; the only axis is where the value lives.

**The invariant everything rests on: a value that isn't written in `kaja.json` is never displayed and never sent to a remote browser**, so kaja.json is safe to commit and only names what a workspace needs.

- **Resolving** (`server/pkg/api/variables.go`) — every variable is resolved once against a `VariableStore` (the OS keychain; the web server binds none) and the environment, keychain → `KAJA_<NAME>` → unset. The keychain wins because the desktop is where the value was typed. A variable whose source holds nothing is **not defined at all**: `${NAME}` passes through literally. `VariableStatus` rides on the configuration responses; `variable_store_available` says whether this machine can store anything.
- **Expanding** — creation parameters in `OpenApp`, and **headers in Go**: the browser sends `${NAME}` unexpanded and `ApiService.InvokeApp` resolves them. It is the single door every call goes through — it expands the headers and **redacts** the resolved values back out of what the app reports exchanging upstream, so the Headers view shows `Bearer ${TOKEN}`. Redaction restores client-sent headers exactly and masks anything the app synthesized by content, only for long enough values, below which a value is indistinguishable from ordinary text.
- **Scripts read resolved values, stored ones included, via a desktop-only binding** — on the desktop the UI runs inside the app's own process. On the web `kaja.variables` is the configuration's own text, because a script runs in a remote browser there.
- **Storing** (`desktop/variable_store.go`) — service `kaja`, account `<configurationPath>#<NAME>`, so two workspaces keep their own value. macOS goes through the **Security framework directly** (cgo, following `bookmark_darwin.go`): kaja ships sandboxed through the App Store, where shelling out to `/usr/bin/security` neither works nor files items under the app. Queries set `kSecUseDataProtectionKeychain` so items are scoped to the app's access group from its `com.apple.application-identifier` entitlement — the trade-off is that an **unsigned local build has no such entitlement** and gets `errSecMissingEntitlement`, so the keychain path only works in a signed build. Windows/Linux keep `go-keyring`. `Available()` probes once; anything but success-or-not-found reports false and the UI asks for the environment instead.
- **A stored value is written the moment the sheet is confirmed**: it is machine state, not file state. **Clearing rides the configuration write**, because what clears it is a row that stopped being stored. The value never travels back out and there is no reveal.
- **The tab** (`Variables.tsx`) is rows in one table, alphabetical: a protobuf map carries no order, so the file's own is arbitrary and re-sorting on every reload would shuffle the table.
  - **The source is the one decision on a row, so it is stated on the row** and the value field is whatever that source needs, the whole field being the control.
  - **Nothing about one row is reported outside that row.** A keychain entry that is missing and an environment variable that is not set turn the *field* amber and say the consequence in a caption under it; the full-width banners this replaced pushed the table down by more than the rows they described. The one thing still said above the table is a `${NAME}` an app uses that **no variable defines**, because that has no row to be said in.
  - **Delete confirms only when there is something to lose** — references, or a value the keychain holds — offering a checkbox for the keychain entry so a variable can go without taking the value with it.
  - A read-only configuration is a **different screen**, not a disabled one, under the read-only banner, which is where setting `KAJA_<NAME>` in the container environment is said.
  - Names are validated against `[A-Za-z_][A-Za-z0-9_]*`, and `${secret}` must be the whole value (`variableExpansion.ts`, unit-tested; mirrored server-side in `validateVariables`).
  - **The table autosaves**, one write at a time, leaving invalid rows in place without writing, and **says nothing about having saved** — everything in Kaja auto-saves, so a receipt here would be one screen claiming a property every other screen has too. A write that *failed* goes to the footer's errors, which is where every such failure goes.
- **Used by is two halves, because the two cost different things** (`variableUsage.ts`). An app's references are in the configuration the window already holds. A script's mean reading the folder, and reading it one file at a time over the wire is what would make the column expensive — so it is **one call**, `ScanScriptVariables`, which walks the scripts folder once where the disk is and answers for every name at once. There is no per-row queue and no cache to invalidate: the scan runs when the screen becomes the one on screen and whenever the workspace names a different set of variables.
- **A script names a variable two ways and both are counted**: `kaja.variables.NAME`, and `${NAME}` inside a value it sends, which the request hop expands. `${env:X}` is the configuration's own spelling and is not one of them. **A draft is not scanned** — a draft has no place on disk.
- **Writing a variable recompiles the apps whose parameters reference it.** An environment change can't be observed, so that only happens on a write or a configuration reload.
- **Every field that ends up as an app parameter is a `VariableSuggestInput`**, custom forms included, suggesting variables when `${` is typed and showing the source rather than the value. Credentials are plain text rather than masked, because what a field holds may be a `${NAME}` naming where the value is kept, and a masked field can't be read back to tell which.

## Generated requests and completions

**Values seen in earlier calls are never written into a generated request.** `defaultInput.ts` only ever emits zero values — and a `Value`/`Struct`/`ListValue` field's zero value is its kaja builder, `kaja.value(null)`, since it has no writable literal. `typeMemory.ts` + `valueCompletions.ts` offer what was seen as editor completions instead, each labelled with the field and call it came from. **The values an app declared are offered on the same list, and first**, because a document saying what a field takes outranks a guess read off what happened to be sent before — and it is there on a field nobody has ever filled in, which is the case memory has nothing to say about.

**A request is an `Input<T>`, so a call may write the fields it means and no others.** The synthesized service stub types its parameter as `Input<Request>` — the generated type with every field optional, at every depth. Nothing in a proto is required, and a field left out is filled with the zero the wire format omits anyway, so the type was the only thing insisting on the whole shape: deleting a field from a generated call turned the line red. A typo or a wrong type is still an error, at any depth.

**How much of that shape a generated call writes out is a `FieldSet`** (`defaultInput.ts`). `all` is every field, because the generated call is where a person meets the request — one they never see is one they never send. `required` is the app's `[required]` mark and nothing else, which for a gRPC or Twirp method is `{}`; it is what the MCP catalog carries, since an agent is handed the declarations of every type a method names and then reads `""` and `0` as values being sent.

**A header belongs to a call, not to a script.** Every generated method takes a second parameter — `CallOptions`, which is headers and nothing else so far — laid over the app's configured ones by name and without regard to case (`mergeHeaders`), the same rule the credential is merged under in Go. The merged set is both what goes out and what the Headers view shows, references intact: a `${NAME}` among the values travels unexpanded like a configured one, so a script in a remote browser sends a value it is not allowed to read. `X-Kaja-App` is refused where it is written rather than dropped on the way — it is what the call is routed by, and a call that set it would be sent under another app's credential.

**There is no run-wide or service-wide header, deliberately.** A binder holding one for "every call in this script" is what makes a token typed for one app reach the next app the script imports; the options are a value, so a local `const` handed to each call is the binding, and the scope is then something the reader can see. The Go door was already per request, so this is a UI-layer change: the merge happens once per call in `client.ts` and rides the meta the door already reads.

**Coming back, `call.withHeaders()` is the one door to what the API answered with** (`callResponseHeaders`): the upstream response headers where kaja transcoded the call, the transport's own where it only forwarded it — the rule `callDurationMs` states about a duration — under lowercase names, since gRPC metadata arrives that way and the one thing a script cannot do is guess which case it was given. A failed call is reported rather than thrown, so it hands back `undefined` beside the headers it was refused with.

**The pair is nested, and asked of the call rather than of the answer.** `{ response, headers }` is a new object holding the message whole, so an API declaring its own `headers` or `response` field is untouched — laying kaja's key over the message would shadow the API's own data. And a `Call` is kaja's type where the message is the app's, which is the same line `X-Kaja-App` is on. Asking the call is also what keeps the rare path from disturbing the common one: `await Service.Method(req)` still means the response. There is **no second spelling** — no `call.headers` beside it, because two doors to one answer is a decision without a capability.

## Kaja's own MCP server

This is the door an agent drives kaja through. The MCP **app** above points the other way; nothing is shared but the protocol's name.

- **Why it's bridged** — scripts execute in the webview's JS context (`ui/src/scriptRunner.ts`, via `new Function`), where the `kaja` object and the service clients live. Editing scripts is file I/O the Go side already does; *running* one has to round-trip into a window. So `server/pkg/mcp` is self-contained and Wails-free, reaches the app only through `mcp.Bridge`, and is unit-tested with a fake — and `server/pkg/agent` is the one thing on the other side of that interface, on both builds.
- **Server** — JSON-RPC 2.0 over HTTP (MCP Streamable HTTP), **dual-era for the reason the MCP app's client is** (`pkg/mcp/protocol.go`): the modern revision dropped the `initialize` handshake, and nearly every client deployed today still opens with one. **The era is read off each request, never held** — the modern one carries its version in `params._meta`, so there is nothing to remember and no branch on which client is on the other end; a version this server does not speak is refused with `-32022` naming the ones it does, since a refusal a client cannot retry on costs it the connection. `server/discover` is modern whatever it carries, being the one method only that era defines, and `initialize` is legacy for the same reason. What the era decides is the framing alone — `resultType`, and the `serverInfo` a modern result carries in its own `_meta` because there is no handshake left to say it in. The cache directives on a listing are **not** era's: they describe the answer, so they are written where the answer is. **`mcp.enabled` in kaja.json is the switch on both builds.** The desktop process reads it at startup and opens a loopback listener guarded by a bearer token; a browser reads it off the configuration it already holds and attaches. Fixing the port and persisting the token keep an installed client working when the switch is turned on again; a port already in use is reported rather than falling back to a random one, which would silently break the configured command. That listener is only `ServeMCP` in front of the switchboard, and it exists for one reason: an agent lives in another process and cannot fetch a `wails://` URL.
  - **A response is a single JSON body, or an SSE stream when something is in front of it.** The answer is identical either way; what the stream buys is a keepalive, so a minute-long `run_script` is not a request that has carried no bytes for a minute — **the idle timeout belongs to the proxy in front**, and a run cut off there is indistinguishable from one that failed. It is offered only when the client's `Accept` says it takes one. Nothing sits between an agent and the desktop, so there the simpler thing is right — **except where the caller asked to hear about its request**, which is streamed whatever the delivery, a notification having nowhere else to go.
  - **A run says what it has done while it is still doing it** (`progress.go`), where the caller passed a `progressToken`. The count is the window's, because only the window knows what the script called; the clock is the server's, because what a caller waits through is measured where it is waiting. The `progress` value is **seconds waited rather than calls made**, unrounded: each notification has to carry a larger number than the last, and a run can go a long way without calling anything — the calls are what the message says. **The window beats rather than reporting per call** (a perf test makes thousands), and it is told on the `run` message whether anyone is listening, so a run nobody asked about costs no traffic. A beat that arrived while the answer was being produced is written **before** the answer, and one nobody kept up with is dropped rather than queued: the next beat says everything it would have.
  - **A tool that writes a file is absent where there is no disk to write** (`Bridge.CanWriteScripts`): `tools/list` drops the writing tools rather than offering them and refusing. A call to one anyway is answered with the sentence saying why.
  - **The Origin is checked before the token is read**, and a request carrying none at all is let through: an agent is a process, and a page is one only where it is this server's own or a local one. A site that resolved a name to the loopback address the agent reaches kaja on would otherwise be a page with an endpoint behind it, and the token is the second guard rather than the only one.
  - **A method with no handler is a 404, which is why `handlerFor` is a lookup rather than a switch.** A streamed answer has sent its status before a handler runs, so whether the method exists has to be settled in front of the choice to stream.
- **The answer is TypeScript, because that is all a script is.** An author writes against an interface; nothing they write is protobuf. So the tools hand back **the generated declarations themselves** rather than a description of the wire format — a declaration can't disagree with the compiler; a second model of one can, and did.
- **Three tools answer everything, and none grows with the API.** `list_services` is an **index**: every app, service and method as one TypeScript signature with a `read`/`write` mark and its HTTP request, filterable, carrying no declarations (dumping the generated modules is what overflowed an agent's context). `describe_method` is the other half: the import line, the signature, the declarations of **every type it names, transitively**, and the call to start from. `describe_type` looks one type up. A miss lists candidates for an ambiguous name and nearest matches for an unknown one, because a dead end costs a whole round trip. Answers are bounded — declarations cut line by line, since one response type can be four hundred properties — and the cut names what to ask for next.
- **The UI settles what the TypeScript is; Go settles what to show.** `ui/src/declarations.ts` re-emits each generated interface and enum from its own AST: member names and type text verbatim, the API's description kept, the `@generated from protobuf field` bookkeeping dropped (it names a wire encoding no script depends on and is the only place protobuf would surface), and the app's marks folded into the JSDoc where a reader meets them. `ui/src/mcpCatalog.ts` gathers those plus the signatures. `server/pkg/mcp` decides the framing: read versus write, the closure, the cut, the failure advice. The `.client` modules are left out.
- **A method's example is the code Kaja already writes** — `describe_method` hands back the same call clicking the method in the tree puts in a draft, asked for its `required` fields alone. The declarations are printed directly over it, so the shape is said once.
- **A generated stub reads as source.** The service object is printed `multiLine`; without it the TypeScript printer puts a synthesized object literal on one line, so a thirty-method service arrived as one enormous line and any line-based reader had to pull the whole module.
- **`kaja.value` is in the generated request, not just the guide.** A field typed `Value`/`Struct`/`ListValue` holds any JSON and its wire shape is a `kind` oneof nobody writes by hand, so such fields used to be omitted — which meant the one place the builder could be learned didn't mention it.
- **The `kaja` object is a declaration too.** `ui/src/kajaModule.ts` writes it once; Monaco backs the `kaja` import with it, the MCP catalog carries it, and `describe_type "kaja"` hands back that exact text. It was described from memory in the guide before, which is how the canvas verbs came to be documented for the editor and invisible to an agent. **So it is the reference, and what is written about a verb elsewhere is spent on teaching rather than on stating the surface.** The guide teaches — a worked example per shape worth writing, plus what is different about being an agent — and names `describe_type "kaja"` for the rest. **An example is what earns its place and a member list is not**: a stale example is caught, since `run_script` reports type errors checked against these same declarations, where a retelling of what a verb does is a second model of the surface. The arithmetic matters too: the guide ships with every session and the declaration costs a call.
- **A run reports the script's type errors, and the checker is the editor's own** (`scriptDiagnostics.ts`). The runner transpiles rather than compiles, so a type error *runs* — only a syntax error stops one. The check asks Monaco's TypeScript worker about a model that is flat like every editor model, because the depth is what makes an import resolve to the same barrel it does in the window. It **reports rather than refuses**, which is what Run already does for the person at the app, and it starts before the run and is read after it, so it costs the run nothing. Two things are left to the run's own error instead: a file that doesn't parse, and an import naming no app, which the compiler answers with tsconfig options a script hasn't got where `prepareTask` names the app.
- **The editor's compiler options mirror the runner's**, `moduleDetection: Force` included: without it a script with no import is a global script to the editor alone, where top-level `await` is an error and two such scripts' top-level names collide.
- **A script has no return value, and that is said rather than discovered.** The transpiler accepts a top-level `return` and the runner's `async` wrapper would honour it, but Monaco flags it and Run goes disabled — so answering by returning works over MCP and produces a file nobody can press Run on. The rule lives in the declaration's header, in the guide, and in the tool description; `RunResult.Result` is still carried so the run report can **correct** a script that returned something rather than printing it under `returned` as if it were the answer.
- **The canvas is the output; `console.log` is where an agent probes.** A script is a file someone opens and presses Run on, so what it has to say goes on the canvas; the transcript is read by the asking agent and nobody else. Naming them side by side is what taught an agent to end every script with `console.log(response)` — so the guide's first example draws, and both the runtime note and the guide say the thing that makes it unnecessary: **`run_script` already reports every call's request and response**, so the only value worth printing is one the script computed.
- **A comment is for what the code cannot say, which in a script is rarely anything.** The rule is stated in the guide and in the tool descriptions of everything that writes a script, because a tool description is the one channel a client cannot drop.
- **A run is reported twice over, from one set of values** (`reportRun` beside `renderRun`). The text is what a client with no structured content is left with and what a person reads in a transcript; `structuredContent` is the same run in the shape a caller parses, which is what `run_script` declaring an `outputSchema` obliges it to carry. Both are cut by the same caps, so neither can say something the other doesn't — except that an oversized payload is **replaced** in the structured half rather than truncated, JSON sliced in half being unparseable, and a report a caller cannot parse loses the calls under it too.
- **A run reports what it drew.** `RunResult.Blocks` is the receipt — each block's kind, and a table's columns and row count. The contents are not echoed: the agent produced them. An agent's run reports cells that never landed rather than passing off blanks as values.
- **An inline run is not anonymous.** `run_script` with `code` stays cheap, but it may not be invisible: an inline snippet runs in **the agent's draft**, so it has a file, a title read off its own code, a row in the sidebar and a console. **One buffer, reused** — eight tries at a call are eight runs of one draft, which is what makes them comparable.
- **The word is agent, not client.** What connects to Kaja's own MCP server is an **agent** wherever the product says it. "Client" is the MCP protocol's own term for the end of the wire that connects, so it stays exactly where the protocol is spoken: `clientInfo`, the `client` field the run message carries, and the Go that reads them.
- **Connecting an agent is a page, not a panel** (`Mcp.tsx`, `mcpAgents.ts`): a screenful of configuration per agent is what a popover had no room for. It reads top to bottom as one sentence — *this is the server, and this is how your agent reaches it.* **An agent is a row in `mcpAgents.ts` and nothing else**, and `configurationKey` is the only half Go has to know about. There is no call log on the page: what an agent runs shows up in the console under the agent draft. And no agent-connected marks either — nothing in the protocol says which of the ten a session belongs to, so the list stays a plain chooser.
- **The list is there whether the server is on or off.** What the switch decides is whether anyone can reach the endpoint, never what it is or which agents can be pointed at it — and a snippet naming a token is worth copying before the server it names is up.
- **The token is shown in full and the snippet carries it.** It is a loopback credential you are about to paste into a config file, so masking it only adds a click. `Regenerate token` is the one verb that invalidates every configuration already pasted, so it **says that first and acts on the second press**, rather than opening a dialog over a page that is already the whole answer.
- **The token is an address, so it outlives the switch on both builds** — the workspace's on the desktop, the browser's on the web, and the server's on neither. It is minted when kaja starts rather than when its server does, so the page names an endpoint and a token before the switch has ever been turned on. `MCPServerInfo` reports the persisted one whether or not the listener is up and **never mints one**: reporting the state of a server must not be what creates its credential.
- **Two marks on the plug, and never both saying the same thing** (`mcpState.ts`, one derivation the sidebar and the page both read). The **dot** answers *is it on*; the **ring** answers *is anyone on it*, and while a request is being served the dot drops out rather than repeating it. The **server** counts requests in flight and reports each change through `Bridge.Activity`; the **UI** decides how long the mark lingers, because that is a question about being seen — calls arrive in bursts of a few milliseconds. A `ping` is a keepalive and doesn't count.
- **Nothing yet stops an agent writing.** The `read`/`write` mark and the guide's "confirm before running a write" are advice an agent may ignore. A gate belongs at the one place every call goes through (`client.ts`), keyed on something the run carries.
- **A failure says what to do about it.** `ui/src/callFailure.ts` classifies a call error while it still has its shape — an HTTP status, a gRPC code, or neither — and neither a status nor a code means the exchange itself broke, the one case where retrying with a different request is guaranteed waste. **A rejected call does not throw** — it is reported and the script carries on with `undefined` — so a script that stopped stopped on its own, usually on that `undefined` a line later, and the report says as much.
- **An agent is given names, not places on disk.** A `ScriptInfo`'s `path` is the script's place under the scripts root, which every tool here resolves, so a listing's own path is handed straight back. Where the workspace sits on the machine serving it is the server's business and no tool needs it — the agent is another process, or another person's browser. The window's own name for the file is the absolute one, and it travels with a run because a console, a history and a sidebar row are all keyed on it.
- **Resources are the guide and the index, and nothing else.** `initialize` returns the embedded guide as `instructions` and it is a resource too, but a client may drop or summarise either — so the script runtime contract is repeated in `run_script`'s **tool description**.
- **Desktop wiring is the same wiring** — `desktop/mcp_bridge.go` is the token, the loopback listener, and the scripts folder as the process that owns it reads and writes it. Everything else is `pkg/agent`'s. **The catalog follows the apps, not the compiler**: it is pushed from an effect on the app list, so a change that compiles nothing — deleting an app, above all the last one — is reflected too. Script mutations made over MCP come back down the window's stream, and the UI live-reloads an open script and keeps the sidebar and open views in step. The create change carries the file's `content`, which is what lets the UI recognise the agent's own buffer being saved.

### The agent session is the whole bridge

`server/pkg/agent`, `ui/src/agentSession.ts`. **There is one switchboard and both builds are it.** Nothing behind it can run a script — the runtime, the `kaja` object and the service clients are JavaScript in a window — so `run_script` goes down a window's stream and the answer comes back up, into the same `runForAgent` in `App.tsx`. A kaja on `demo.kaja.tools` is driven by a local agent exactly as the desktop one is, because it is the same code.

- **A session is something a browser offers, not something the server has** — though whether it offers one is the workspace's to say (`mcp.enabled`), not the browser's. A browser with the switch on makes up a token and holds a stream open under it; that is the only way a session comes into being. **The token is the address of a browser, not a key to the server**: it is never anywhere but that browser's storage, the server persists nothing, and a token nobody has attached with is a 401. That is the whole security model, and it is what makes this safe at a public demo even with the switch on: a visitor's session is reachable only by the token their own browser made up and kept. Turning it off closes the session and leaves the token where it is.
- **The desktop is the degenerate case of that, not a second mechanism.** When its switch is on, its window attaches over the mux its webview already fetches its calls on: a stream is a response the scheme handler writes in pieces, exactly as it writes a server stream's frames. The token is the one the process persists.
- **`Scripts` is one implementation over the Api service**, so an agent and the window it is driving are looking at one folder resolved by one rule. Whether the writes are refused is the service's answer, not the build's. `CanWrite` is what `tools/list` drops the write tools on, and a write returns a `ScriptChange` — one value, because it has one job on each side: what the agent is answered with, and what every window is told.
- **A browser's token is the one thing kept in `localStorage`** rather than in `storage.ts`, because localStorage is shared between an origin's tabs *and* fires `storage` when it changes, so connecting in one window attaches the others as they are. **It holds the address and nothing else**: the switch is `mcp.enabled`, so a flip reaches the other tabs down each one's own configuration stream rather than through the `storage` event, which is left to do the one job only it can — telling a tab that the token was rolled under it.
- **A reconnection waits, but never past the window coming back.** A dropped stream backs off, and sitting out that backoff on a server that is answering is the whole of what makes the page look stuck — so `focus`, `visibilitychange` and `online` cut the wait short. The two waits are named apart for the same reason: an endpoint that is not up yet is the server *starting*, one already named with no stream on it is this window *connecting*.
- **Several windows on one token is normal, so one is on duty** — the most recently focused — and every window is told whether it is, because a run's console is in memory in the window that ran it. The desktop has one window and is always it.
- **Giving up on a run's answer gives up on the run.** A run the agent walked away from is a script still going in the window, holding whatever it opened, with nothing left to report to. So the session sends an `abort` and the window does what **Stop** does to that one run: aborting the signal alone is not enough, because a script sleeping between two calls never looks at it.
- **Discovery does not need a live window; only `run_script` does.** The catalog a window pushed is kept as long as the session is, so the read-only tools answer across a reload. With no window `run_script` fails **immediately**, and a window that goes away mid-run fails its run on the stream's closed channel rather than waiting out the timeout.
- **Whoever holds the disk reads a saved script itself** and hands the window source; the script's own path travels with it, because that is what the run lands under. So the window is never asked to read a file, on either build, and `run_script` has one shape.
- **Everything is plain HTTP outside the Api service** (`agent.Mount`), as `/app` already is: the Api service is about the workspace, this is about a door. **No CORS header is set on any of them**, so a page on another origin cannot drive the endpoint.
